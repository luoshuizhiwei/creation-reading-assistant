# 原生 Android 移动端全景梳理与公开发布体检

> 日期：2026-09-19  
> 面向：非技术项目负责人 / 产品决策者  
> 范围：`android/` 原生 Android 产品线；不评价 Electron 桌面端  
> 性质：只读产品与工程体检，不是当前工作区的发布验收报告

## 0. 一句话结论

移动端已经不是 Demo，也不是“缺几个功能”的早期应用。它是一套功能面很宽、阅读器内核投入很深、已有大量自动化测试和真机证据的中大型本地阅读产品。

它现在最大的风险不是功能少，而是：

1. 产品承诺比已统一验证的能力更宽；
2. 同一工作区叠加了大量尚未集成的改动；
3. 历史绿灯属于不同时间、不同切片，尚未收敛成一个可发布版本；
4. 备份、同步、升级、隐私和发布签名仍需作为完整系统验收；
5. 用户主价值尚未在首页、引导、信息架构和验收标准中统一表达。

因此，当前正确动作不是继续横向加功能，而是进入“产品收敛与发布工程”阶段。

## 1. 本次确认的产品定义

以下不是从代码猜出来的，而是本次与项目负责人逐项确认的产品决策。

### 1.1 产品是谁

- 核心用户：重度本地阅读者。
- 核心定位：深度阅读助手，不是泛内容平台，也不是单纯电子书查看器。
- 两条同级主线：
  - 知识沉淀：阅读内容能被标注、记录、定位、搜索、回顾和再利用。
  - 习惯养成：阅读时长、进度、目标、连续阅读和统计能形成正反馈。
- 阅读器体验是地基；简洁与隐私是产品约束。

### 1.2 首个公开版边界

- 全部现有顶层入口保留，并作为正式产品面接受审查。
- TXT 与 EPUB 是正式支持格式；Markdown 不纳入首版正式承诺。
- 手机是正式支持设备；平板尽力兼容，不作为首版逐页精修的硬门槛。
- 离线时核心功能完整可用；数据本地优先，同步由用户主动开启。
- AI 是 BYOK 可选增强；没有 AI 配置时，阅读、标注、搜索、统计和备份仍必须完整。
- 开源免费，通过独立 APK / GitHub Releases 首发。
- 不以日期换质量；全部功能不退，发布时间服从完整性与可靠性。

### 1.3 这组决定的真实代价

“全部入口都保留”意味着首版不是最小可用产品，而是一个完整面较大的公开产品。每个入口都必须满足四个条件：

1. 用户知道它解决什么问题；
2. 主要任务从开始到结束都能走通；
3. 进程重启、版本升级和异常中断后数据不乱；
4. 有与承诺相匹配的自动化和真机证据。

页面能打开、按钮能点、单元测试很多，都不能替代这四个条件。

## 2. 给小白看的系统地图

可以把应用理解为六层，而不是几百个 Kotlin 文件。

```text
用户看到的页面
  首页 / 书架 / 灵感 / 统计 / 我的 / 阅读器 / 搜索
        ↓ 发出动作
页面状态与协调层
  ViewModel：加载数据、处理点击、决定页面当前显示什么
        ↓ 调用业务能力
业务能力层
  导入、书库识别、阅读排版、翻页、搜索、标注、TTS、目标、同步
        ↓ 统一读写
数据仓库层
  Repository：把页面与数据库、文件、网络隔开
        ↓
本地与外部数据
  Room 数据库 / 应用私有书籍副本 / 设置 / SAF 授权目录 / WebDAV / 局域网
        ↓ 横向保护
测试、迁移、备份、安全、发布与真机验收
```

这套分层的意义是：页面不应该自己直接改数据库，阅读器也不应该把“屏幕上第几个字”直接当成永久进度。当前项目已经有这些分层意识，但规模变大后仍需要持续约束。

### 2.1 当前体量

本次静态盘点得到：

- 主 Kotlin 文件约 512 个；
- JVM 测试文件约 280 个；
- Android 设备测试文件约 28 个；
- 主应用是单 `app` 模块，另有 `benchmark` 模块；
- 数据库已到版本 15；
- 最低 Android 7.0（API 24），目标 Android 15（API 35）；
- 当前默认版本为 `0.5.1` / `versionCode 3`。

这说明它已具备真实产品规模，但仍是“单大模块”。单模块不是立即缺陷，不过会让多人或多 Agent 并行时更容易发生文件所有权冲突和集成困难。

## 3. 五个顶层入口分别在做什么

顶层导航定义见 [`AppNavigation.kt`](../../android/app/src/main/java/com/creationreadingassistant/ui/navigation/AppNavigation.kt)。

### 3.1 首页：今天为什么要打开应用

首页承担“继续阅读、最近行为、完成与灵感摘要”等聚合职责。它不应变成所有功能的第二套入口。

产品判断：

- 应把两条主线汇合在这里：继续读什么，以及最近沉淀了什么 / 今日目标如何。
- 首页的成功标准不是卡片数量，而是用户能在几秒内继续最重要的任务。
- 若首页、书架、我的阅读都重复展示同一批信息，应按任务拆分，而不是继续叠卡片。

### 3.2 书架：本地内容的可信入口

当前书架不只是网格列表，已经包含：

- 单文件导入与目录授权；
- 应用内目录浏览和智能识别；
- 来源索引、更新识别和私有稳定副本；
- 搜索、筛选、分类、标签、书单和批量操作；
- 书籍详情、统计、笔记摘要和删除撤销。

已有的重要优点：使用 Android SAF，不申请“管理所有文件”权限；目录来源与应用私有副本分离；来源失效后仍可保留可读副本。

仍需产品收口的问题：

- [`2026-09-18-android-shelf-maturity-plan.md`](../plans/android/2026-09-18-android-shelf-maturity-plan.md) 记录了“读完”状态在书架识别和入口上的缺口；不能把有数据字段等同于用户可管理。
- 书单顺序字段的历史值与迁移策略需要单独处理，不能和低风险 UI 修复混在一起。
- “最近添加”和“修改时间”在 SAF 下使用同一底层时间，文案需解释，避免制造并不存在的精确语义。

### 3.3 阅读器：整个产品最深、也最危险的核心

阅读器已覆盖的能力非常多：

- TXT / EPUB 加载；
- 滚动和分页；
- 多种翻页效果、点击区域、硬件按键；
- 目录、进度跳转、搜索、选区、划线、笔记和灵感；
- 正文规则净化与源文本坐标映射；
- TTS、字典、纸张、字体、护眼和昼夜模式；
- 阅读会话、进度保存、退出时强制落库；
- 大文件有界读取、缓存上限和部分故障降级。

阅读器最难的不是“把字画出来”，而是保持四种位置一致：

1. 原始书籍中的位置；
2. 净化或排版后屏幕上的位置；
3. 搜索、划线和笔记引用的位置；
4. 下次恢复和跨设备同步的位置。

只要这四套坐标混用，就会出现“划线跳错、搜索点开错位、重启回不到原处、规则开关后笔记漂移”等严重问题。现有架构已经专门建设 locator、offset map、source/display contract，这是项目真正有价值的技术资产。

最近证据见 [`2026-09-18-android-device-verification.md`](../qa/2026-09/2026-09-18-android-device-verification.md)：翻页闪烁/空白、夜间冷启动、真实章节号和交互停顿曾被真机发现并修复。这也证明，仅靠 JVM 测试无法发现阅读器的全部问题。

### 3.4 灵感：知识沉淀的成品区

当前数据层已有划线、笔记、灵感及其变体；阅读器可以保存这些内容，并支持回到原书位置。

产品上必须厘清三者：

- 划线：原文证据，核心是位置可靠；
- 笔记：用户对原文的解释，核心是上下文和可编辑性；
- 灵感：可脱离单次阅读继续发展的想法，核心是组织、检索和再利用。

若三者只是不同页面中的相似卡片，用户会困惑。首版应明确转化关系，例如：划线可附笔记，笔记可提炼为灵感；删除原书、更新源文件、修改净化规则后，引用关系必须有清楚行为。

### 3.5 统计：阅读习惯主线的反馈面

统计已有时长、趋势、热力图、状态、目标环、年度总结等组件；阅读会话和进度也有独立表。

正式发布前不能只检查图表是否好看，还要统一这些口径：

- 什么情况下开始计时；
- 切后台、锁屏、TTS、临时查阅时是否计时；
- 异常超长会话怎样过滤；
- “读完一本”“读了一章”“连续阅读一天”分别如何判定；
- 修改系统时间、时区或跨午夜后如何处理；
- 数据恢复后是否会重复累计。

统计一旦数字不可信，激励主线反而会伤害信任。

### 3.6 我的 / 设置：不是杂物间，而是控制中心

当前“我的”已经包含：阅读档案、阅读设置、目标、标签/分类/书单、存储、局域网同步、WebDAV、AI、字典、隐私、安全、诊断、关于和更新。

优点是能力完整；风险是信息密度过高。设置搜索已经存在，说明信息架构确实进入需要检索的规模。

建议把它分成稳定心智：

- 阅读体验；
- 阅读记录与目标；
- 内容组织；
- 数据、备份与同步；
- 可选增强（AI、字典等）；
- 隐私、诊断与关于。

## 4. 两条核心用户旅程

### 4.1 知识沉淀闭环

```text
导入书籍
  → 打开并可靠定位正文
  → 选中文字
  → 划线 / 写笔记
  → 可提炼为灵感
  → 在全局搜索或灵感页找到
  → 精确回到原文上下文
  → 备份、恢复、升级后关系仍成立
```

发布门槛：TXT 和 EPUB 都要分别走完全链；不能只证明“保存成功”，还要证明“以后找得到并回得去”。

### 4.2 阅读习惯闭环

```text
设定目标
  → 开始真实阅读
  → 正确记录活跃时长与进度
  → 暂停、后台、退出时及时收口
  → 首页 / 统计给出可信反馈
  → 提醒在正确时间、正确条件触发
  → 第二天愿意继续阅读
```

发布门槛：通知触发、设备重启后的提醒恢复、跨日和异常会话必须有真机证据。历史交接曾明确指出通知与重启恢复证据不足；应以当前代码重新验收，不能沿用旧结论或旧绿灯。

## 5. 数据到底保存在哪里

### 5.1 书籍与正文

- 用户通过系统文件选择器或目录授权提供来源；应用无需传统存储权限。
- 导入后可建立应用私有副本，降低原文件移动、授权失效带来的风险。
- 来源引用用于判断原文件是否仍在、是否更新，以及是否可能是同一内容。

### 5.2 结构化数据

Room 数据库保存书籍、正文元数据、分类、标签、书单、来源引用、进度、会话、章节已读、划线、笔记、灵感、规则、页索引和同步状态等。数据库定义见 [`AppDatabase.kt`](../../android/app/src/main/java/com/creationreadingassistant/data/local/AppDatabase.kt)。

### 5.3 设置与凭据

- 普通偏好保存在应用设置中；
- 局域网同步令牌、WebDAV 密码和 AI Key 使用安全存储；
- 系统备份规则明确排除这些凭据，避免换机或云备份带走秘密。

### 5.4 备份不等于数据库复制

应用的 JSON / ZIP / WebDAV 备份通过 [`JsonBridge.kt`](../../android/app/src/main/java/com/creationreadingassistant/feature/sync/JsonBridge.kt) 选择性导出。当前明确包含书籍、灵感、进度、会话、笔记、划线、标签、分类、书单、书单关系和章节已读等。

但数据库中还有来源引用、阅读规则、页索引、定位缓存、纠错等表。它们未全部出现在导出信封中。这里需要逐表做产品决定：

- 必须恢复的用户资产；
- 可以重建的缓存；
- 应明确丢弃的设备状态；
- 若丢失会悄悄改变行为的配置。

在完成“数据库表 → 备份字段 → 恢复行为”矩阵之前，不能宣称“整库无损备份”。

## 6. 同步与隐私边界

### 6.1 已有能力

- 本地 JSON / ZIP 导入导出；
- WebDAV 连接、备份列表、上传和恢复；
- 局域网配对与同步框架；
- Legado 阅读进度导入；
- GitHub Releases 更新检查。

### 6.2 需要直说的风险

[`network_security_config.xml`](../../android/app/src/main/res/xml/network_security_config.xml) 明确允许明文 HTTP，以兼容局域网桌面端。代码层会拒绝公网地址，这是必要防线；但同一局域网中的主动攻击者仍可能嗅探或篡改通信。

因此公开版应：

- 在配对页面明确说明“仅可信局域网使用”；
- 不把局域网同步描述成端到端加密；
- 后续以 TLS + 配对时证书指纹固定作为根治方案；
- 对 WebDAV 默认要求 HTTPS，局域网 HTTP 例外要有明确提示；
- 在 AI 请求前说明将发送的正文范围和目标服务商。

### 6.3 文案与事实不一致

[`OnboardingOverlay.kt`](../../android/app/src/main/java/com/creationreadingassistant/ui/onboarding/OnboardingOverlay.kt) 当前使用“全格式阅读”“多端无缝互联”“云同步”等强承诺。它们与本次确认的 TXT/EPUB 正式支持、本地优先、可选同步边界不一致。

建议将引导改成可证明的承诺，而不是愿景广告：

- 本地优先的 TXT / EPUB 深度阅读；
- 标注、笔记、灵感和搜索形成沉淀链；
- 目标与统计帮助持续阅读；
- 用户主动选择局域网或 WebDAV 备份；
- AI 为自带服务的可选增强。

## 8. 目前最值得肯定的部分

1. **本地优先不是口号。** SAF、私有副本、Room、本地备份和可选同步形成了真实结构。
2. **阅读器坐标问题被认真对待。** source/display/locator 的契约意识，是标注和恢复可靠性的根基。
3. **大文件与缓存有边界。** 有界 ReadingUnit、投影上限、LRU 和并发锁显示内核不是无控制地堆内存。
4. **测试文化较强。** 不只测 UI，还覆盖数据库迁移、规则、定位、搜索、导入、缓存与并发。
5. **真机反馈能追到根因。** 最近对闪帧、冷启动、排序竞态、真实章号和快速翻页的修复有可解释证据。
6. **权限相对克制。** 没有申请管理全部存储，摄像头也声明为非必需硬件。
7. **发布骨架已存在。** GitHub Actions 已包含 Android 测试、Lint、签名 Release、签名校验、APK、源码包和 SHA-256 产物设计。

## 9. 当前最严重的六个风险

### 风险 1：工作区不是一个可描述的版本

本次检查时：

- 分支：`main`；
- HEAD：`2a428851`（2026-09-15）；
- 工作区共 304 项；
- 209 项为已跟踪文件修改，95 项为未跟踪文件；
- 约 258 项涉及 `android/`。

在这种状态下，无法回答“当前版本到底包含哪些功能”和“2515 项测试是否覆盖了全部现状”。这是发布前第一阻塞，不是 Git 整洁偏好。

### 风险 2：产品承诺与实际支持边界不一致

“全格式”“无缝多端”“云同步”等文案会让用户按比实际更高的标准评判。公开版应只承诺已完成端到端验证的能力。

### 风险 3：备份恢复的“整库”语义未被证明

备份包含大量核心资产，但不是数据库全表镜像。需要明确哪些表是用户资产、哪些可重建、哪些会影响阅读行为。

### 风险 4：两条主线都有页面，但未形成统一验收

知识沉淀和习惯养成各自有大量组件，却缺一张从入口到备份恢复的发布矩阵。局部测试通过容易掩盖跨页面链路断点。

### 风险 5：发布工作流“写好了”但尚未证明可用

[`release.yml`](../../.github/workflows/release.yml) 的 Android 流程结构合理，但文件注释仍写着签名 keystore 尚未配置、`android-v*` 发布不可用。需用非生产测试签名或正式密钥环境做完整演练，再决定是否删除旧 TODO。

### 风险 6：单项目负责人 + 多 AI 的集成风险

AI 很擅长完成窄功能，却容易产生：

- 重复组件和重复入口；
- 各自正确、组合错误；
- 测试只覆盖自己切片；
- 文档结论过期；
- 未提交文件与他人所有权交叉。

需要把“产品切片、文件所有权、统一集成、独立验收”当作固定生产流程，而不是临时协调。

## 10. 建议的收敛路线

### 阶段 A：冻结横向扩张，形成唯一候选基线

目标：先回答“我们到底准备发布什么”。

1. 盘点 304 项工作区变更，按来源、产品切片、完成状态和依赖分组。
2. 区分：已完成待集成、开发中、实验文件、诊断工件、桌面端无关改动。
3. 为 Android 建立串行集成顺序，不再让多个 Agent 同时改公共导航、数据库、设置和阅读器宿主。
4. 每个切片先跑定向测试；全部合并后才跑统一门禁和真机验收。
5. 得到一个可重复构建、可标记版本的候选基线。

退出条件：`git status` 中剩余项都有明确归属，不存在“没人知道能不能删/该不该进版”的文件。

### 阶段 B：用用户旅程而非页面清单验收

至少建立以下八条端到端旅程：

1. 新用户首次打开 → 导入测试 TXT → 阅读 → 退出 → 恢复位置；
2. 导入测试 EPUB → 目录跳转 → 翻页 → 重启恢复；
3. TXT 划线/笔记 → 全局搜索 → 回原文；
4. EPUB 划线/笔记 → 灵感 → 回原文；
5. 设目标 → 阅读计时 → 跨日统计 → 提醒与重启恢复；
6. 原文件移动/更新/授权失效 → 私有副本与用户数据行为符合预期；
7. 完整备份 → 清洁环境恢复 → 核对所有用户资产和引用；
8. 从旧公开版本升级 → 数据库迁移 → 继续阅读与同步。

每条旅程都要分别记录：自动化证据、真机证据、未覆盖项和失败后的数据状态。

### 阶段 C：校准产品表达

1. 重写新手引导，删除不可证明的“全格式”“无缝”等绝对承诺。
2. 让首页同时回答“继续读什么”和“最近沉淀/目标怎样”。
3. 明确划线、笔记、灵感的关系和转化路径。
4. 统一统计口径，并在必要位置给用户解释。
5. 将 AI、WebDAV、局域网同步明确标为可选增强，展示数据边界。

### 阶段 D：完成数据安全矩阵

为每张 Room 表和每类文件建立表格：

| 数据 | 是用户资产吗 | 本地备份 | WebDAV | 局域网同步 | Android 系统备份 | 可重建吗 | 删除语义 |
|---|---|---|---|---|---|---|---|

重点核对书籍副本、来源引用、划线/笔记/灵感、书单关系、阅读规则、进度、会话、章节已读和定位信息。

### 阶段 E：发布演练

1. 确认开源许可证、第三方声明、隐私说明和反馈渠道。
2. 配置并保护 Android 正式签名；证明密钥备份和轮换责任。
3. 在干净环境通过 CI 构建签名 APK。
4. 校验 APK 签名、SHA-256、源码包和 Release Notes。
5. 从 GitHub Releases 安装/升级，验证应用内更新检查正确识别 Android 标签。
6. 用至少两类真实手机完成发布候选验收；平板记录为兼容观察，不阻塞首版。
7. 发布后保留回滚与已知问题说明。

## 11. 项目负责人今后怎样判断一项功能是否完成

不要问“代码写完了吗”，改问下面七个问题：

1. 用户为什么需要它？
2. 从哪里进入，完成后得到什么明确结果？
3. 失败、取消、后台、杀进程后会怎样？
4. 它读写了哪些数据，升级和恢复后还在吗？
5. TXT 与 EPUB 是否都成立？如果不成立，界面是否诚实说明？
6. 哪些是自动化证据，哪些是真机证据，哪些尚未覆盖？
7. 它和现有页面、设置或数据是否重复或冲突？

当七个问题都有明确答案，功能才接近“完成”。
