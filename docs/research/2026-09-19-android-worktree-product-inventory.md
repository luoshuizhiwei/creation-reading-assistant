## 2. G0：Git 对象链恢复——所有集成工作的前置门

### 2.1 已确认事实

仓库是 partial clone：

- `remote.origin.promisor=true`
- `remote.origin.partialclonefilter=blob:none`

HEAD commit 和根 tree 本身存在，但递归读取树或生成 diff 时会遇到缺失对象。现场表现包括：

- `git diff --numstat` 触发远端补取对象后返回 `not our ref`；
- `git diff-files --numstat` 同样无法稳定完成；
- `git fsck --connectivity-only --no-reflogs` 报主 index cache-tree 无效；
- 多个旧 worktree 的 index cache-tree 也引用缺失对象；
- HEAD 递归树中至少有子 tree 无法读取；
- 当前网络还出现 GitHub 443 无法连接。

这不是“Git 状态有点乱”，而是无法可靠回答“工作文件相对 HEAD 到底改了哪些行”。

### 2.2 为什么必须先处理

在这种状态下直接暂存或提交有四个风险：

1. 无法完整审查提交内容；
2. hunk 级拆分可能漏文件或误带他人改动；
3. 新建验证 worktree 可能失败；
4. 提交后才发现基线对象不可读取，失去可复核性。

### 2.3 建议恢复策略

不要在当前目录里盲目删除 index、清理 `.git/objects` 或运行破坏性 Git 命令。

优先采用可恢复方案：

1. 保存当前 `git status`、工作区路径清单和本地领先提交信息；
2. 网络可用时，在新目录创建 origin 的完整 clone；
3. 验证新 clone 的 `git fsck`、HEAD、origin/main 和历史对象完整；
4. 单独验证本地提交 `2a428851` 能否安全转移；
5. 按本清单的切片边界，将当前工作文件复制到新 clone 后重新生成 diff；
6. 当前目录保留为只读证据，直到新 clone 中所有切片和哈希核对完成。

## 4. 各切片的产品解释与处理建议

### S01 父表 UPSERT 防数据丢失——最高优先级

**用户能感知的问题**：读了很久后，某次保存、导入或同步让书籍相关的进度、会话、笔记、高亮、正文缓存和来源引用突然消失。

**根因**：父表过去使用 SQLite `INSERT OR REPLACE`。SQLite 的 REPLACE 不是“原地覆盖”，而是先 DELETE 再 INSERT；外键开启时会触发级联删除或置空。

**当前工作区动作**：

- `BookDao`、`InspirationDao`、标签/分类/书单父表改用 Room `@Upsert`；
- 新增 `ParentUpsertCascadeSafetyTest`，覆盖书籍、灵感、标签、分类、书单及其子表关系；
- 注释记录了一次设备数据库副本实验：普通父表写入曾让阅读会话从 208 行降到 5 行。

**真实 diff 边界（恢复后）**：

- S01 只取 `BookDao.kt` 中 `upsert` / `upsertAll` 的 `@Upsert` hunk；同文件新增的 `getAllActive` 和 `activeIds` 分属进度导入与搜索，不能夹带；
- `InspirationDao.kt` 只取父记录 `upsert` 的 `@Upsert` hunk；
- `TaxonomyDao.kt` 只取 `TagDao`、`CategoryDao`、`ShelfDao` 三个父记录写入 hunk；关系表自身的 REPLACE 不在本切片；
- 新增 `ParentUpsertCascadeSafetyTest.kt` 作为隔离 Room 回归；
- Room v15 schema 与 `AppDatabase.kt` 不属于 S01。

以当前 `15.json` 反查全部外键后，数据库只有 `books`、`inspirations`、`tags`、`categories`、`shelves` 五张表被其他表引用；S01 已覆盖这五类父表。DAO 中其余 `REPLACE` 均用于子表或叶表，不能仅凭注解名称机械替换。

**判断**：这是独立于 UI 的 P0 数据安全修复。应成为 Git 恢复后的第一个候选提交。

**必须验证**：

- 新增 androidTest 真正执行，不只是编译；
- 普通更新、批量更新、软删除和同步合并均不触发子表丢失；
- 不修改用户真实书库，使用隔离测试数据库。

### S02 Room v15 搜索索引瘦身

**用户价值**：降低搜索索引占用，避免一本约 6.65 MB 中文书生成约 328 MB 索引时继续重复存储 term 索引。

**当前实现**：

- schema 版本升至 15；
- `MIGRATION_14_15` 删除与复合主键前缀重复的 `index_search_terms_term`；
- 保留按书删除和查询需要的索引；
- 新增 `15.json` schema 快照。

**真实 diff 边界（恢复后）**：

- `AppDatabase.kt`：版本 14→15 与 `MIGRATION_14_15`；
- `DatabaseModule.kt`：注册 14→15 迁移及同步注释；
- `app/schemas/.../15.json`：新 schema 快照；
- 14/15 schema 结构化比较显示实体数同为 26、view 数同为 0，声明索引的唯一差异是 v15 移除 `search_terms|index_search_terms_term|term`；
- `dropPartialIndexes(db)` 还会在迁移校验前临时删除手工部分索引，正常开库后由 `CreateIndexCallback` 重建；这是既有迁移框架行为，不是 v15 新增的数据改写。

**当前缺口**：`AppDatabaseMigrationTest.kt` 相对远端没有修改，尚无 14→15 定向迁移测试，也没有覆盖到 15 的完整历史链测试。因此“只删一个冗余索引、数据行不变、保留 book 索引、部分索引正常重建”尚未形成可执行证据。

**判断**：方向合理且 schema 静态差异符合意图，但当前仍是“实现已写、迁移证据缺失”，不能直接形成候选提交。补齐 14→15 与完整链测试后，才可与 S01 分开集成；不能把“当前混合工作区能编译”当成迁移提交可用。

**门禁**：14→15、旧版本连续迁移到 15、schema identity、迁移前后搜索结果一致、数据库实际体积对照。
