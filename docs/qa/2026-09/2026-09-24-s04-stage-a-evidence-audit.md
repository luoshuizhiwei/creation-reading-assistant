## 审计项 1 · `snap-02-progress.tar` 体积约为相邻快照的一半

### 1.1 证据

### 1.2 能确认的结论

1. **差异确实存在且量级约一半**：1,120,616,960 ≈ 2,270,000,640 × 0.494。

   **因此这不是「快照越往后越小」的单调漂移**，而是 02 这一个点的异常。
3. **02 与两侧的大小差远大于内容变化所能解释的量**：01→03 之间只多了约 6 KB，
   而 02 比 01 少了约 1.15 GB。一个「造出阅读进度」的动作不可能产生 GB 级的**净减少**。
4. **`tar -t` 均退出 0、顶层条目均为三项**：报告 §2.2 末句明确写了六份快照全部如此。

## 审计项 3 · 更正超出源码证据的表述

用户点名两处：「EPUB 更新永远不生效」「只传 `expectedBookId` 即可修复」。
**注意：第二句在报告中并非原文**，原文是「替换路径必须传 `expectedBookId`」（报告 `:485`）。
审计按「该修复主张是否被源码支持」来核，同时给出两处的更正。

### 3.1 证据

| 来源 | 内容 |
|---|---|
| `EpubRepository.kt:108` | `val validated = EpubParser.parse(context, selectedUri)` —— **确未传** `expectedBookId` |
| `EpubRepository.kt:60-65` | `openStoredEpub` **传了** `expectedBookId = stored.id`（对照写法，`:154-159` 的后置解析也传了） |
| `EpubParser.kt:57` | `val id = expectedBookId ?: ("epub_" + uri.toString().hashCode().toString(36))` |
| `EpubParser.kt:59-60` | `val epubFile = File(context.filesDir, "books/epub/$id.epub")`；`if (!epubFile.exists() \|\| epubFile.length() == 0L) { /* 才复制 */ }` |
| 报告 `:243-262`、`:477`、`:485` | 机制定位与「永远不生效」表述 |

### 3.2 表述 ①：「EPUB 更新永远不生效」 —— **超出证据，应更正**

**能确认的（源码层面，审计独立核对通过）**：

- `replaceStoredEpub` 在 `:108` 调用 `parse` 时**确实没传** `expectedBookId`，
  而同文件 `:63` 与 `:157` 两处**都传了** —— 这是一个**真实且明确的**不一致。
- `EpubParser.kt:57` 在未传时回退到 `"epub_" + uri.toString().hashCode().toString(36)`；
  `:59-60` 的早退分支 `if (!epubFile.exists() || epubFile.length() == 0L)` 确实会在
  该派生 id 的文件已存在时**跳过复制**，沿用旧副本。

**不能确认的 —— 「永远」二字没有被证明**：

早退分支**只在「该 derived-id 的文件已存在且非空」时**才命中。该 id 由
`uri.toString().hashCode()` 派生，即**依赖来源 Uri 的字符串**。这意味着：

- 若某次替换的 `selectedUri` 派生出的路径**尚不存在**（例如用户换了一个不同的来源文件、
  或该派生副本此前被清理过），早退**不命中**，复制**会**执行，替换**可能**生效；
- 因此「永远不生效」是**一个未加限定的全称判断**，而现有证据只覆盖
  「同一 Uri、派生副本已存在」这一种现场（阶段 A 仅此一次 EPUB 重同步实测）。

> **更正建议**：把「EPUB 更新永远不生效」改为
> **「在『同一来源 Uri 且派生副本已存在』这一现场下，EPUB 来源更新为 no-op（阶段 A 实测 1 次）；
> 其他现场未经实测，不得断言『永远』」**。
> 缺陷本身**成立**，但**范围**必须收敛到已实测的现场。

### 3.3 表述 ②：修复主张「（只）传 `expectedBookId` 即可修复」 —— **不成立，且会引入新缺陷**

这是本审计**最重要的一条更正**。

若把 `:108` 改为传 `expectedBookId = stored.id`，则 `parse` 会走
`id = stored.id` ⇒ `epubFile = filesDir/books/epub/<stored.id>.epub`。
**而 `EpubRepository.kt:89` 的 `target` 正是同一个文件**：

```kotlin
// EpubRepository.kt:89  —— target
val target = File(context.filesDir, "books/epub/${stored.id}.epub")
// EpubParser.kt:59      —— 传了 expectedBookId = stored.id 后的 epubFile
val epubFile = File(context.filesDir, "books/epub/$id.epub")   // id == stored.id ⇒ 与 target 同一路径
```

于是 `parse` 的早退分支判断的**就是 target 自己**。而 target 在替换前**必然已存在且非空**
（它就是待替换的旧正文）⇒ **早退必然命中** ⇒ **来源字节依然从未被读取**。

**后果链条（源码可推，非推测）**：

1. `validated.cachedEpubPath` 指向 target（旧副本）本身；
2. `:129-131` 把 `validatedFile`（= target，旧字节）复制进 `staging` —— **staging 里是旧字节**；
3. `:135-146` 把 target 挪进 backup；
4. `:148-151` 把 staging（**旧字节**）promote 成 target；
5. `:165` `computeFileHash(target)` 算出的仍是**旧哈希**；
6. `:179` `backup.delete()` 删掉备份。

⇒ **替换会「成功」返回、正文内容不变、hash 不变，且比现状更糟**：
现状至少还会产生「新 size + 旧 hash」这个**可见的矛盾配对**（报告 §3.3 正是靠它发现的缺陷）；
改后 size 与 hash 会**一致地都是旧值**，矛盾信号**消失**，缺陷转为**静默**。

> **更正建议**：**不得**把「传 `expectedBookId`」写成修复方案。
> 该改动会使早退分支**从「偶发命中」变成「必然命中」**，
> 把一个**可观测**的缺陷变成一个**静默**的缺陷。
> 正确方向应是让替换路径**强制读取来源字节**（例如 parse 前使早退不可能命中，
> 或让替换路径走一条不复用旧副本的解析入口）—— **具体方案由开发窗口判定**，
> 本报告只指出「只传 `expectedBookId` 不构成修复，且可能更糟」。

> 补充审计发现（与报告 §9-4 同源，源码已核对）：`EpubParser.kt` 的流程是
> **先落盘到 `books/epub/$id.epub`（`:62-95`）→ 之后才 `ZipFile(epubFile)` 校验（`:98`）**，
> 失败时 `catch` 只 `staging.delete()`（`:93` 区域）而**不删已落位的 `epubFile`**。
> 报告 §4.2.1 关于「孤儿副本文件」的机制定位**与源码一致**，该条**成立**。
> 这进一步说明：仅改 `expectedBookId` **也修不掉孤儿文件**（落盘位置虽变到 target 名下，
> 失败时仍不清理，且会污染 target 的落盘路径）。**两处须一并设计**。

### 3.4 后续建议

1. 报告 §9-1 与 §9 末段应**收敛表述**：去掉「永远」，限定到实测现场；
   并把「只传 `expectedBookId`」从修复建议中**移除**或标注为「已审计：不构成修复」。
2. 开发窗口若修复，需**同时**处理：① 强制读取来源字节（消除 no-op）；
   ② 落盘移到校验成功之后（消除孤儿文件）。二者同源，不可只改其一。
3. 修复后**必须**重跑阶段 A 的 EPUB 路径（现状 FAIL 未修），
   并用「新 size **且**新 hash」作为通过判据 —— 注意修复后若只看到「size/hash 都还是旧值」，
   要警惕 §3.3 所述的**静默退化**。

### 4.2 能确认的结论

**A. JVM 测试确有价值的真实面**：

- **真实 `EpubParser`**：测试用真实 `ZipOutputStream` 构造 EPUB 并走**真实解析器**，
  不是把 parser mock 掉 —— 解析链路是**真**的。
- **真实文件系统**：`FakeFileOps` 默认**直通真实文件系统**（KDoc `:488` 称其为
  「行为等价性钉子」），字节级断言（target 逐字节存活等）落在**真实磁盘**上。
- **真实 `computeFileHash` + 32 MiB 阈值**：大文件置 `null` 的分支**有** JVM 覆盖（覆盖项 2）。
- **真实回滚语义**：`backupReady` / `promoteStarted` 的进程内回滚（覆盖项 4、8）**有** JVM 覆盖。

**B. 但以下全部是替身，不等价于真实环境**：

| 维度 | JVM 测试中的形态 | 真实环境 | 是否被 JVM 覆盖 |
|---|---|---|---|
| **DAO 层** | `bookDao` / `readingProgressDao` 为 **MockK 假对象**（`io.mockk.mockk` 注入，`:69-70` 区域） | **真实 Room** DAO + SQLite | ❌ **未覆盖** |
| **事务 / SQL 约束** | 假 DAO 不执行 SQL，无外键、无 `ON CONFLICT`、无事务 | Room 真实行为（`:177` `if (bookDao.update(updated) == 0) bookDao.upsert(updated)` 依赖真实返回值） | ❌ **未覆盖** |
| **SQLite 并发** | `Dispatchers.Unconfined`（`:65`）⇒ **单线程串行**，无并发 | 真实多线程 / 多进程访问 | ❌ **未覆盖** |
| **设备路径** | `filesDir` = `TemporaryFolder`（`:84`） | 设备 `/data/data/…/files`，含 SELinux、配额、存储满、SAF 权限失效 | ❌ **未覆盖** |
| **进程被杀** | 无法模拟 | K2/K3/K4 残留现场 | ❌ **未覆盖**（报告 §7 D4 已登记） |
| **`Uri` 行为** | `mockkStatic(Uri::class)` 静态 mock（`:80`） | 真实 SAF Uri 与权限 | ❌ **未覆盖** |

**C. 与报告 §7 D1–D8 的对应关系（逐条核过）**：

| # | 情形 | 报告状态 | 是否有 JVM 覆盖 | 真实环境覆盖 |
|---|---|---|---|---|
| D1 | `renameTo(backup)` 失败 → `copyTo(backup)` 中途失败 | 未覆盖 | ✅ **有**（覆盖项 8，经 `FakeFileOps` 注入） | ❌ |
| D2 | 后置持久化失败 ⇒ 从 backup 逐字节还原 | 未覆盖 | ✅ **有**（覆盖项 4） | ❌ |
| D3 | 协程取消 ⇒ 回滚 | 未覆盖 | ✅ **有** | ❌ |
| D4 | 进程被杀 / 断电残留（K2/K3/K4） | 未覆盖 | ❌（不可模拟） | ❌ |
| D5 | 大文件（>32 MiB）`content_hash` 置 null | 未覆盖 | ✅ **有**（覆盖项 2） | ❌ |
| D6 | `renameTo` 跨卷 / 权限失败 | 未覆盖 | ❌ | ❌ |
| D7 | 同一本书被两个入口**并发**替换 | 未覆盖 | ❌（`Unconfined` 单线程，结构上无法覆盖） | ❌ |
| D8 | 备份复制长度校验 | 未覆盖 | ⚠️ **部分**（长度校验分支已注册为「失去的覆盖」，见下） | ❌ |

> **关于 D8 的重要限定**：`EpubRepositoryReplaceTest.kt` KDoc（`:54-58`）**明确列出**
> 「本片之后仍然失去的分支覆盖（不得声称已覆盖）」三条：
> ① 长度相同但内容不同的损坏备份不会被 `require` 拦下（只比长度）；
> ② 回滚自身失败；③ `require` 通过后、`target.delete()` 之前进程被杀（无 fsync）。
> **这份自述是诚实的，审计确认其与源码一致**（`:142` `require(backup.length() == target.length())` 只比长度）。
> 因此 D8 不得写成「已覆盖」。

### 4.3 不能确认的边界

- **假 DAO 的返回值是否忠实于 Room**：`:177` 依赖 `bookDao.update()` 返回 `0` 与否来分流
  `update` / `upsert`。MockK 的返回值是**测试手工 `coEvery` 设定的**，
  **不证明**真实 Room 在该场景下的返回行为。**审计不能确认**真实 Room 的行为与之相符。
- **`TemporaryFolder` 上的 `renameTo` 语义**：`FakeFileOps` 直通真实文件系统，
  但 `tempFolder.root` 与设备 `filesDir` **可能不在同一卷**，
  因此「跨卷 `renameTo` 失败」（D6）在 JVM 上**可能根本无法复现** —— 这既解释了 D6 为何未覆盖，
  也意味着**即使覆盖了也不能代表设备行为**。
- **本报告未运行任何测试**：以上覆盖判断**基于源码与 KDoc 静态阅读**，
  **未**通过实际执行测试来核验（本轮为只读审计，未跑 Gradle）。

### 4.4 后续建议

1. **引用纪律**：凡引用 JVM 测试结果，**必须**注明「假 DAO + `TemporaryFolder` + `Unconfined`
   单线程」，不得表述为「已在真实 Room / SQLite 上验证」。
2. **D7（并发）在 JVM 结构上不可覆盖**：`Dispatchers.Unconfined` 使并发测试无意义。
   建议改用真实 dispatcher + `runTest` 多协程，或明确登记为「只在真机/集成层可测」并长期保留在 §7。
3. **补充 instrumented 覆盖**：`grep` 确认 `androidTest` 中**无** `replaceStoredEpub` 测试。
   但 MIUI 宿主当前**阻止** Compose instrumentation（`result code=102`，报告 §8），
   故**短期内不可行**；在宿主问题解决前，D1–D8 的真实环境覆盖**只能**靠
   「手工 UI 操作 + `adb` 只读取证」，且**不得**把 instrumentation 的零结果写成通过。
4. **D4 / D6 属于结构性不可测**：进程被杀与跨卷失败无法通过常规测试覆盖，
   建议在文档中长期标注为「设计层保障，非测试可及」，避免被误当作待补测试项反复开合。
