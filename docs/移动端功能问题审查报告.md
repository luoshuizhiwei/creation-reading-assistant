# 移动端功能质量审查报告

> 审查对象：`mobile/src`（React 18 + Capacitor 6 + TypeScript 移动端 App）
> 审查角度：功能正确性 / 数据完整性 / 健壮性 / 性能 / 集成
> 方法：全量静态分析 + 关键问题源码逐行复核（已亲自确认，非仅依赖工具结论）
> 日期：2026-07-20

## 总体结论

工程质量**整体偏高**：存储层有 try-catch 兜底、SQLite 为权威源、删除书籍会清理 progress/sessions/notes/highlights、导入有 commit 校验与回滚、进度保存有节流与写队列、Capacitor 插件调用有可用性检查。数值计算（百分比、时长）普遍有边界保护，未发现 NaN/除零类崩溃。

但存在 **3 个严重级问题**（会导致空白屏 / 数据丢失 / 卡顿）和 **7 个一般级问题**（健壮性 / 数据一致性 / 性能）。其中 3 个严重 + 2 个一般已逐行复核确认。

---

## 一、严重级（建议尽快修）

### 🔴 S1 · 首屏加载快照无 `.catch`，启动异常会永久空白屏
- **位置**：`src/App.tsx:144-150`
- **代码**：`void loadMobileSnapshot().then(async (loaded) => { ... setSnapshot(loaded); });` —— 没有 `.catch`
- **根因**：`loadMobileSnapshot()` 内部 `initializeMobileStorage()` 在 SQLite 打开 / 建表 / 查询异常，或 `migrateLegacySnapshot()` 首次迁移中途抛错时，会 reject。`setSnapshot` 永不执行。
- **影响**：一旦首启迁移或某次 SQLite 操作抛错，App 永远停在 `emptySnapshot` —— 屏幕空白、无任何报错提示，用户会以为数据全丢了（实际 SQLite 里可能还在，但进不去）。这是最高优先级。
- **修复方向**：`loadMobileSnapshot()` 后加 `.catch`，失败时 `setMessage` 提示并尝试回退到 localStorage 快照兜底，保证至少能进入应用。

### 🔴 S2 · 局域网同步用远程数据整体替换本地灵感与阅读会话，本机独有记录会被静默丢弃
- **位置**：`src/hooks/useMobileSync.ts:238-245`
- **代码**：
  ```ts
  const merged: MobileSnapshot = {
    ...snapshot,
    inspirations: pull.inspirations.map((item) => item.payload), // ← 整段替换
    books: mergedBooks,        // ← 按 id 合并（正确）
    progress: mergedProgress,  // ← 按 id 合并（正确）
    sessions: pull.sessions.map((item) => item.payload),          // ← 整段替换
  };
  ```
- **根因**：`books`/`progress` 都做了 `by id` 合并，但 `inspirations`/`sessions` 直接 `pull.*.map(payload)` 覆盖本地。若桌面端 pull 返回语义是增量、或未回显本机刚 push 的记录，本地独有的灵感/会话就丢了。同步前备份仅 1 份，覆盖后旧值即不可恢复。
- **影响**：阅读会话（用于阅读时长、连续天数统计）和未被回显的灵感被清空；统计失真且无法恢复。
- **修复方向**：对 `inspirations`/`sessions` 也改成像 `importMobileSnapshot` 那样按 id 与本地 `snapshot` 合并（union + 必要时合并远程优先）。

### 🔴 S3 · 阅读进度每 1.5s 触发整库 localStorage 全量序列化写入，大库卡顿且 Web 场景丢写
- **位置**：`src/services/mobile-storage-core.ts:399-418`（尤其第 410 行）
- **代码**：`localStorage.setItem(STORAGE_KEY, JSON.stringify(normalized));` —— **无视 `selectedSections` 参数**
- **根因**：`selectedSections` 只用于 `mirrorSnapshotToSQLite`，localStorage 分支永远写全量。V2 阅读器进度节流仅 1.5s（`ReaderProgressRepository.ts:34`），频繁触发整库 `JSON.stringify` + `setItem`。
- **影响**：几百 KB 正文预览 + 数百本书 + 大量笔记时，主线程同步写入每 1.5s 一次，低端机掉帧。当 localStorage 配额（约 5–10MB）撑满，`setItem` 抛错被 catch 吞掉 —— 因 SQLite 是权威源，无永久丢失，但 localStorage 兜底彻底失效；纯 Web 预览/调试（无 SQLite）场景会真正丢写。
- **修复方向**：localStorage 分支按 `selectedSections` 局部更新，或高频 progress 变更只写 SQLite、不每 1.5s 全量序列化。

## 二、一般级（健壮性 / 数据一致性 / 性能）

### 🟠 G1 · 删除分类时未清理 `inspiration.categoryIds`，产生悬挂引用 ✅已复核
- **位置**：`src/features/profile/hooks/useLibraryManagers.ts:128-147`
- **根因**：category 分支只清理 `book.categoryIds`（128-136）；`inspirations` 的清理被锁死在 `kind === "tag" && targetTag?.type === "inspiration"` 分支（138-147），删除**分类**时不会触发。
- **影响**：删除分类后，灵感的 `categoryIds` 仍指向已删除 id；若某处按分类筛选灵感会漏判/误判。无崩溃，但数据不一致。
- **修复方向**：category 分支同步 `snapshot.inspirations.map(i => ({...i, categoryIds: i.categoryIds?.filter(c => c !== id)}))`。

### 🟠 G2 · 删除书籍 `onConfirm` 无 try/catch，文件删除失败会卡死对话框 ✅已复核
- **位置**：`src/features/shelf/ShelfPage.tsx:313-318`
- **代码**：`const next = await deleteMobileBook(snapshot, book.id); onSnapshotChange(next); ...; onConfirm(null);` —— 整个 async 体无 try/catch
- **根因**：`deleteMobileBook`（`mobile-storage-books.ts`）先删记录提交、再删本地文件；文件删除失败时它内部回滚记录并 `throw`。异常向上冒泡，后面 `onSnapshotChange` / `setDetailBookId` / `onMessage` / `onConfirm(null)` 均不执行。
- **影响**：确认对话框保持打开、无任何提示，用户需手动关闭。属于“记录已回滚但 UI 卡在删除中”的不一致。
- **修复方向**：`onConfirm` 体包 try/catch，异常时 `onConfirm(null)` 关闭对话框并 `onMessage` 报错。

### 🟠 G3 · 阅读中“打开灵感”绕过 `leaveReader`，当次阅读会话时长丢失
- **位置**：`src/App.tsx:218-225`（V2）/ `:248-255`（Legacy）；`MobileReaderV2View.tsx:209-238`
- **根因**：阅读会话仅在 `leaveReader` 经 `addMobileReadingSession` 落库；直接卸载阅读器只 flush 进度，不写 session。普通返回键走 `leaveReader` 没问题，唯独“阅读中保存灵感并跳转”这条路径漏了。
- **影响**：这次阅读时长不计入统计，连续天数/时长偏低。

### 🟠 G4 · 在线 TTS 请求无超时 / 无 Abort，接口挂起时卡在 “loading”
- **位置**：`src/services/mobile-tts.ts:452-475`（`fetchOnlineTTS`）
- **根因**：`fetch` 默认无超时/AbortSignal；接口无响应时 `playChunk` 一直 `setStatus("loading")`，只能退出页面。
- **影响**：在线朗读遇慢/挂死接口时，播放条长时间 loading，无兜底。

### 🟠 G5 · 在线 TTS 暂停后 `play()` 不会真正 resume，而是重播当前块
- **位置**：`src/services/mobile-tts.ts:349-363` / `:477-484`
- **根因**：`play()` 的 resume 分支只覆盖 `local` 引擎；在线引擎 paused 时 `play()` 重走 `playChunk(currentIndex)`，等于重播当前段开头。
- **影响**：在线 TTS 暂停再继续，重复朗读当前段落开头，体验偏差。

### 🟠 G6 · `downloadBookToMobile` 用闭包 `snapshot` + `setSnapshot(prev => { next = prev })` 反模式读取最新状态，存在竞态脆弱
- **位置**：`src/hooks/useMobileSync.ts:142-149`
- **根因**：闭包捕获渲染时旧快照，再借 `setState` 更新函数读 `prev` 取最新值（副作用 hack）。若在 `setSnapshot` 调度前发生另一次写入，Race 下可能基于过期状态保存。
- **影响**：低概率竞态覆盖并发修改。

### 🟠 G7 · 每次 `snapshot` 变更都全量重算统计 / 继续阅读列表，大库有性能开销
- **位置**：`src/App.tsx:73-74`（`buildMobileStatsSummary`）、`src/features/home/HomePage.tsx:137-140`（`getContinueBooks`）
- **根因**：统计与“继续阅读”对 `snapshot` 全量敏感，但多数变更（阅读进度 1.5s 一次保存）并不需要重算这些昂贵指标，且阅读中并不展示。
- **影响**：叠加 S3 写入开销，低端机更明显。（属优化级，但建议与 S3 一并处理）

## 三、做对的地方（正面，供参考）

- 存储层 `saveMobileSnapshot` 有 try-catch，SQLite 为权威源，S3 不会丢永久数据；
- 删除书籍 `deleteMobileBook` 清理 progress/sessions/notes/highlights/shelves，引用完整性好；
- 导入有 commit 校验与回滚（`importMobileSnapshot` 按 id 合并，是 S2 的正确范本）；
- Capacitor 调用（`openNativeReader`、`isLocalTTSAvailable`）有可用性 / 平台双重检查；
- 空书架 / 空灵感 / 空搜索均有 EmptyState，AI/TTS/文件读写普遍有 try-catch。
