# TXT 目录识别规则集草案（backlog 第 9 项备料）

> 2026-07-27 起草。状态：**备料，未实施**。正文规则均凭经验起草，
> 标「待验证」的条目需要拿真书跑过再定稿。
> 对应 `docs/plans/legado-feature-backlog.md` 第 9 项。

## 1. 定位：默认规则的「每本书救济通道」，不是替换

现状 `feature/reader/doc/TxtChapterDetector.kt` 的设计原则是**宁可少认，不可乱认**：
只认「第X章 / 卷X / 序章类 / Chapter N」四类，刻意不认裸数字开头，
且平均章节 < 300 字整体作废。这个默认**保持不动**——它保证了任何书导入都不会
出现几百个伪章节的灾难。

但代价是：分章只写「1」「一、」「【3】」的书，目前识别不出目录，且用户**没有任何
救济手段**。本方案补的就是救济通道：

- 默认识别失败或识别错时，用户在**这本书**上手动换一套更宽松的规则重新识别；
- 规则选择按书持久化，不影响其他书；
- 用户手选规则 = 用户背书，合理性检查从「整体作废」降级为「弹提示但尊重选择」。

## 2. 规则集草案

实现形态：每条规则 = `id + 显示名 + 正则列表`。应用时取**默认四类 ∪ 所选规则**的并集
（宽松规则只做加法，不会让原本能认的「第X章」反而认不出）。

通用约束沿用现状：标题独占一行、trim 后 ≤ 40 字符。
下表正则均为 Kotlin `Regex` 语法，`NUM` 沿用现有定义
`[0-9０-９零〇一二三四五六七八九十百千万两]`。

| id | 显示名 | 正则 | 命中示例 | 必须不命中 | 风险 |
|---|---|---|---|---|---|
| `builtin` | 标准（默认） | 现有四类，见 TxtChapterDetector | 第12章 夜行 / 卷三 / 楔子 / Chapter 7 | 正文任意行 | 低 |
| `num-dot` | 数字+标点开头 | `^\s{0,4}\d{1,4}\s*[.、．:：,，]\s*\S.{0,29}$` | `1. 序幕` / `12、重逢` / `3：夜谈` | `1.5 倍速`（待验证：小数）/ `2023.5.1 晴`（日期，会误中，见 §4） | **高** |
| `num-bare` | 纯数字独行 | `^\s{0,4}\d{1,4}\s*$` | `1` / ` 42 ` | `2024`（年份独行会误中，靠合理性检查兜） | **高** |
| `cn-num-dot` | 中文数字+顿号 | `^\s{0,4}[零〇一二三四五六七八九十百千两]{1,8}\s*[、.．]\s*\S.{0,29}$` | `三、夜访` / `十二、归途` | `一、二等奖`（无法区分，接受误差） | 高 |
| `bracketed` | 括号包围 | `^\s{0,4}[【〔\[（(]\s*(?:第?\s*NUM{1,12}\s*[章节回卷部篇]?\|\d{1,4})\s*[】〕\]）)]\s*.{0,30}$` | `【第三章】` / `（12）` / `[3] 重逢` | `（笑）`（纯文字括号不含数字） | 中 |
| `en-extended` | 英文扩展 | `^(?:part\|section\|book\|act\|prologue\|epilogue\|interlude)\s*[0-9ivxlcdm]{0,8}\b.{0,30}$`（忽略大小写） | `Part II` / `Prologue` / `ACT 3` | `particle physics`（`\b` 保证） | 低 |
| `md-heading` | Markdown 标题 | `^#{1,3}\s+\S.{0,38}$` | `# 第一部` / `## 楔子` | `#话题标签`（要求 # 后有空格） | 低 |
| `custom` | 自定义正则 | 用户输入单条正则 | — | — | 用户自负 |

**暂缓不做（有需求再议）**：
- 分隔线包围式标题（`====` 下一行是标题）：需要多行上下文，现有检测器是单行判定，
  改造面大，真书里也少见；
- 「排除正则」（命中则强制不算标题）：先不做，规则并集 + 合理性提示够用；
- 规则自动推荐（试跑多套规则选章节数最合理的）：v2 再说，先给手动。

## 3. 交互与持久化

1. **入口**：目录 Sheet（`TocSheet`）底部加一行「目录不对？换一套识别规则」，
   仅 TXT 格式显示。灵感来源 legado 的「目录规则」，但只做单选不做规则市场。
2. **规则选择页**：列出上表规则，每条**实时预览**——用该规则跑一遍全文，
   显示「识别出 N 章」+ 前 5 个标题。预览在 IO 线程跑，全文已在内存
   （`PlainTextDocument`），几 MB 文本单次正则扫描百毫秒级，可接受。
3. **应用**：选定后重建章节列表。**进度不丢是免费的**——阅读位置真源是全书字符
   偏移（`LegacyOffsetCodec` / pager 的全书偏移），章节只是偏移区间的划分，
   重划分后按当前偏移反查所在章即可（现有 `chunkIndexForOffset` 同思路）。
   书签/高亮/灵感存的也是偏移 + locator，同样不受影响。
4. **持久化**：所选规则 id（custom 则连同正则串）按书存。落点二选一，实施时定：
   - `book_content` 表加列（要 Room 迁移，记得先 `dropPartialIndexes` —— 见项目
     记忆里的部分索引地雷）；
   - 或 `BookEntity.payload` JSON 里加 key（免迁移，但要过同步链路的 payload 合并，
     需确认 electron 端不会丢字段）。**倾向后者，先确认同步不丢**。
5. **合理性检查降级**：用户手选规则后，`MIN_AVERAGE_CHAPTER_CHARS` 检查不再整体
   作废，改为应用前弹提示：「平均每章只有 N 字，可能识别错了，确定用这套规则？」
6. **页索引失效**：章节划分变了，pager 的分页缓存指纹必须变。确认
   `PageIndexStore` 的指纹输入里含章节边界（或含规则 id），否则换规则后
   旧页码缓存会错位。**这是实施时最容易漏的一步。**

## 4. 已知误报场景与对策

| 场景 | 会误中的规则 | 对策 |
|---|---|---|
| 日记体正文「2023.5.1 晴」 | num-dot | 数字限 1–4 位挡不住；靠预览让用户看见章节数异常 + 合理性提示 |
| 年份独行「2024」 | num-bare | 同上；num-bare 本来就是给「纯数字分章」的书专用的 |
| 正文引用列表「一、…二、…」 | cn-num-dot | 合理性提示（平均章节过短） |
| 全角数字「１２、」 | num-dot 目前不含全角 | 定稿时决定：`\d` 换成 `[0-9０-９]`（倾向加上） |

## 5. 定稿前必须做的验证（待验证清单）

1. 找 3–5 本真实的非标准分章 TXT（纯数字分章、「一、」分章、【】分章各至少一本），
   逐条规则跑预览，校对章节数与标题；
2. `num-dot` 对小数（`1.5 倍`）与日期行的误中率——若不可接受，收紧为
   「标点后必须紧跟非数字字符」；
3. 单次正则扫描 5 MB 文本的耗时真机实测（预期 < 200ms，超了就上进度指示）;
4. payload 持久化方案：造一本带自定义规则的书走一轮局域网同步，确认字段不丢。

## 6. 单测用例（实施时直接抄）

```
// num-dot
"1. 序幕"        -> 命中

"2023.5.1 晴"    -> 已知误中，接受（§4）
// num-bare
"42"             -> 命中
"42 是答案"      -> 不命中
// cn-num-dot
"三、夜访"       -> 命中
"三十五、归途"   -> 命中
// bracketed
"【第三章】"     -> 命中
"（笑）"         -> 不命中
// md-heading
"## 楔子"        -> 命中
"#话题"          -> 不命中
// 并集语义
"第12章 夜行"    -> 任何规则组合下都命中（默认规则始终参与）
```
