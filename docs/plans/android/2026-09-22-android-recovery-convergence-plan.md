## 4. 六个执行阶段和退出条件

### A. 建立可追溯快照和唯一任务表

1. 确认写入窗口停止，记录分支、HEAD、逐文件修改清单、源码/配置/测试哈希；未跟踪文件也纳入。HEAD 本身不能标识这个脏工作树。
2. 提交尚未获授权时，用范围明确的补丁与未跟踪源码副本保留可回退记录；验证能在隔离目录重建相同内容。设备私人数据、凭证不混入普通工件。
3. 每个任务记录：ID、用户行为、文件所有权/共享文件 hunk、依赖、风险类型、实现状态、测试状态、原始证据、下一步。状态采用“待核实/待决定/待修复/待验证/已关闭/延期”，延期必须附理由和依赖影响。
4. 缺陷分开记：产品故障、验证缺口、工程集成风险、体验建议。同一根因只计一次。

退出：20 个历史切片及新增修复都有归属；当前功能清单可查；无一项仅凭“Agent 已完成”关闭。此时才能给出可信的剩余项数，不报估算完成百分比。

### B. 数据与核心风险核实

- 优先核实 S01 父表更新是否保留子记录，S02 支持的数据库升级链是否保留数据。
- 核对 S03 索引竞态/撤销与 S04 来源更新后的正文、哈希、索引、标注坐标；不要用修 UI 代替修数据链。
- 核对 S05 分类/筛选和 S06 进度/启动/快翻；复用已存在的后续修复证据。
- S14 并行调查：书籍正文、来源引用、进度、会话、标注、规则、设置分别是否备份/恢复，有无重复累计或丢失。
- 复核六接口清理；DAO 查询方法删除不会本身改变 schema，但仍需编译实际调用方和相关测试。

退出：风险有当前证据和明确处理方式；影响数据完整性的未验证项不能写作通过。

### C. 按依赖集中修复，附带必要整理

- 最多两路互不重叠的实现。共享数据模型、Room/Gradle、导航和公共模块由一个集成者独占。
- 优先数据故障、错误坐标、无效入口和核心操作阻断。同一模块的小修合并一轮复核。
- 整理限于已证明冗余的代码、过时注释、明确的目录/包名问题；架构重写、统一改名、全仓格式化单独立项。
- 保留函数即使暂时零引用也必须有理由；删除则记录引用证据和功能判断。反射、Hilt、Room、Manifest、资源及 profile 引用都不能仅靠 Kotlin 文本搜索排除。
- D F-4 文案、F-5 换行等默认记入 P3，除非实际阻断操作，不单开全量验收轮。

退出：每项变更有定向验证，当前版本需要交付的行为得到保持，未解决项已明确归类。

### D. 冻结候选，集中验证

1. 固定源码/配置/测试清单与哈希；冻结期间其他窗口不写代码、不改变构建输入。
2. 单一构建所有者串行运行全量 JVM、Lint、主 Debug APK 与 androidTest APK 构建。结果包含失败/错误/跳过，现存警告按影响评估；不要求无依据的零警告。
3. 核对 test package、runner、真实 package 声明和可用测试列表；DurationUnitToggleEntryTest 的真实 FQCN 含 `stats.components`。测试目录不一致本身不是产品故障。
4. MIUI 启动阻塞先限时诊断一个最小代表用例；成功再批跑。相同失败点不反复全套重试，不擅改安全设置。确需新增设备/权限的变更单独呈现证据和方案。62 条未完成保持 BLOCKED，直到执行或获得说明充分的替代覆盖。
5. 独立验收由当前用户指定的 D/Qoder 负责；未另行指定的任务沿用 WorkBuddy。Codex 核对证据，不重复同一轮手机操作。
6. 真机仅竖屏：导入→打开→阅读→搜索/标注→退出重进；设置作用域；时长/完成态；受控数据的升级与备份恢复。只对变更影响范围复验已关闭用例。
7. 时长 >=24h、完读 pill 等使用可控夹具/隔离测试数据；禁止为凑用例直接改用户现有数据库。TalkBack 语义断言与实际播报证据分别记账。320dp 测试可用竖屏受控布局，不要求横屏。
8. 记录安装前通知权限、字号、旋转、常亮、无障碍和必要应用设置的原值，再操作；缺失基线只能记“无法证明恢复”，不可用上一轮值冒充本轮原值。
9. 必须对应同一 APK 哈希和源码清单。既有证据若输入未变且覆盖有效可以复用；相关输入变更才重新验证。

退出：每个必需用例有可追溯结果；故障、阻塞、未测、明确排除分开列出。环境阻塞不等于产品失败，也不等于产品通过。横屏按用户要求排除。

### E. 整理版本并选择最终目录

- 提交前展示候选文件/hunk、依赖顺序、遗留资产去向；经用户明确授权后才 stage/commit。数据基础提交先于依赖它的功能；每个提交边界应可编译，关键边界有定向测试，末尾再做完整门禁。
- Android 提交只包含直接相关源码、必要配置和测试；报告与证据不默认打包提交。既有桌面改动单独保护。
- 先对原/恢复目录进行文件与历史差异核对及 Git 对象完整性诊断；本次不把原仓库损坏状态视为已恢复或仍损坏的最新结论。
- 原 Git 健康：在隔离集成目录处理原目录独有改动与恢复提交；不往脏 main 直接合并。
- 原 Git 仍不完整：优先用健康仓库作为最终基础；也可继续使用恢复目录。需要原路径时，在保留旧目录副本、合并独有资产后切换路径，不强行往坏仓库移植提交。
- 换目录后重建并检查 SDK/local.properties、绝对路径脚本、Agent/IDE 项目路径及安装产物来源。仅路径改变做相称的冒烟测试；实际合并改变代码则扩大到受影响验证。
- 最終目录来源与内容核对完成后保留原/恢复备份；没有授权不删除、不推送。

退出：一个明确的健康开发入口、工作区资产归属清楚、可以复现构建与回退。该状态不等于已公开发布。
