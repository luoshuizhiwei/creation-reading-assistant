## 0. 问题陈述

上一轮已修掉**进程内异常**的回滚（阶段分流 `oldCopyMovedToBackup` / `newCopyPromoted`）。
但 `reselectPlainText` 的「文件替换」与「Room 提交」是**两个独立持久化动作**，
中间被 `SIGKILL` / 掉电 / 系统回收进程打断时，磁盘上会留下**不一致的三元组**
（DB 记录 / `internalFile` / `backup`），而当前代码**没有任何恢复入口**。

更具体的风险在函数入口：

```kotlin
// ShelfImporter.kt:947-948
staging.delete()
backup.delete()      // ← 无条件
```

`backup.delete()` 在**尚未判定**这份 backup 是不是「上次崩溃后仅存的旧正文」之前就把它删掉。
若上次崩在「旧文件已挪入 backup、新文件尚未落位」那一点，`internalFile` 已不存在，
**backup 就是用户仅存的那份正文** —— 下一次修复一开始就把它删了，等于把可恢复的旧内容永久销毁。

同类入口在 EPUB 侧同样存在：`EpubRepository.kt:89-90`。

## 2. 命名与定位的两个前提

### 2.1 残留文件是「按文件名」命名，不是按 bookId

```kotlin
// :943-946
val safeName = fileName.replace(Regex("""[\\/:*?"<>|]"""), "_")   // 来自"本次所选文件"的显示名
val internalFile = File(internalDir, safeName)
val staging = File(internalDir, "$safeName.repairing")
val backup  = File(internalDir, "$safeName.backup")
```

`safeName` 取决于**用户这次选了哪个文件**。若用户改选了一个改了名的副本，
则 `internalFile` 路径与 DB 里旧的 `local_content_path` **不是同一条**。

两个后果，设计必须覆盖：

- **恢复入口不能只按固定文件名找**，必须扫描 `filesDir/books/<bookId>/` 目录、
  按后缀识别 `.repairing` / `.backup`，再用 DB 记录判定归属。
- 同一目录下**可能同时存在多组** `<nameA>.backup` / `<nameB>.backup`（跨次改名累积），
  设计需允许「多组残留」并逐组判定。

### 2.2 DB 侧可用的判据与其可信度

| 判据 | 来源 | 可信度 |
|---|---|---|
| `books.local_content_path` | S9 写入 | 强（直接指向目标文件） |
| `books.content_hash` | S9 写入 `newBookHash` | **仅小文件可信**（≤32 MiB 才是 MD5；大文件按既定策略写 `null`） |
| `books.size` | S9 写入 | 弱（不同内容可能同长度） |
| `book_files.size` / `local_uri` | S9 写入 | 弱，同上 |

`computeFileHash`（`ShelfImporter.kt:432-446`）语义：`len > MAX_HASH_BYTES(32 MiB) → null`；否则返回 MD5，
空文件/读取失败**抛出**（上一轮已修）。

⇒ **「有无可信 hash」是本次设计的一等公民**：决定某组残留能否被自动判定。

## 3. 最小状态机

### 3.1 状态定义

以「某本书的一次 reselect」为粒度。设：

- `T` = 目标正文文件（DB 的 `local_content_path` 所指，或本次将写入的那条路径）
- `B` = 备份文件（`<name>.backup`）
- `S` = 暂存文件（`<name>.repairing`）
- `DB` = `books` 行（含 `content_hash` / `size` / `local_content_path`）

状态取值（对每个文件）：`absent` / `old`（旧正文）/ `new`（本次新正文）/ `partial`（写了一半）。

| 状态 | 触发点 | T | B | S | DB 指向 | 含义 |
|---|---|---|---|---|---|---|
| **CLEAN** | 初始 / S10 之后 | 存在 | absent | absent | 与 T 一致 | 一致，无残留 |
| **PREPARING** | S4 期间 | 存在(old) | absent | partial | 旧 | 新副本还没写完 |
| **SWAPPING** | S5 完成、S6 未完成 | **absent** | **old** | new | 旧 | **T 缺失，B 是仅存的旧正文** |
| **PROMOTED** | S6 完成、S9 未提交 | 存在(new) | old | absent | **旧** | 文件已是新内容，DB 仍描述旧内容 |
| **COMMITTED** | S9 提交、S10 未执行 | 存在(new) | old | absent | **新** | DB 已提交，B 是过期备份 |
| **DEGRADED** | 任一环节写入残缺 | 任意 | 任意 | 任意 | 任意 | 无法判定 |

> `SWAPPING` 与 `PROMOTED` 的差别只在 `T` 是否存在；
> `PROMOTED` 与 `COMMITTED` 的**文件形态完全相同**，只能靠 DB 区分 —— 这正是 §4 的核心难点。

### 3.2 迁移与崩溃点

```
CLEAN ──S3'──▶ PREPARING ──S5──▶ SWAPPING ──S6──▶ PROMOTED ──S9──▶ COMMITTED ──S10──▶ CLEAN
   ▲               │                 │                │                │                │
   │             (K1)              (K2)             (K3)             (K4)             (K5)
   └─────────────────────────── 进程内异常走 catch（已修） ───────────────────────────┘
```

| 崩溃点 | 位置 | 崩溃后状态 | DB 描述的内容 | 危险度 |
|---|---|---|---|---|
| **K1** | `:948` 之后、`:960` 之前 | PREPARING | 旧 | 低（T 完好）——**但 S3 已删掉了上次的 backup** |
| **K2** | `:966` 之后、`:967` 之前 | **SWAPPING** | 旧 | **极高：T 缺失，B 是唯一副本** |
| **K3** | `:970` 之后、`:988` 之前 | PROMOTED | 旧 | **高：需把 B 恢复回 T** |
| **K4** | `:1016` 之后、`:1017` 之前 | COMMITTED | 新 | 中：B 已过期，可清理 |
| **K5** | `:1017` 之后 | CLEAN | 新 | 无 |

### 3.3 入口守卫（最小、可立即落地的一条）

`S3` 的 `backup.delete()` 必须改为**条件清理**，规则：

```
入口见到 backup 已存在：
  ① 若 T 不存在                      → 上次崩在 K2：B 是唯一副本
                                       ⇒ 不删 B；先恢复（见 §4），恢复成功再继续
  ② 若 T 存在且能证明 DB 描述的就是 T  → 上次崩在 K4：B 已过期
                                       ⇒ 安全删除 B，继续本次流程
  ③ 其它（T 存在但无法证明）          → 上次崩在 K3 或状态不明
                                       ⇒ 不删 B、不覆盖 T；**中止本次修复并报错**
```

`staging.delete()`（`:947`）可保留无条件删除：`S` 永远是「本次所选文件的未完成副本」，
用户手上仍有来源文件，删掉不丢用户数据。**唯一例外**见 §4.2 规则 R5。

## 4. 判定规则（含「无法判定则保留并报错」）

### 4.1 核心判定表

设 `H(x)` = 对文件 `x` 计算 MD5（仅在 `x` 存在、且 `x.length() ≤ 32 MiB` 时可得）。
`DBh` = `books.content_hash`。`DBp` = `books.local_content_path`。

| 情形 | 条件 | 判定 | 动作 |
|---|---|---|---|
| **R1** T 缺失、B 存在 | — | 上次崩在 K2（T 是唯一正文，却在 backup 里） | **把 B 恢复为 T**；不删 B 直至恢复校验通过 |
| **R2** T 存在、B 存在 | `H(T)` 可得 且 `DBh == H(T)` | DB 已提交**新**内容（K4） | 保留 T；**删除 B** |
| **R3** T 存在、B 存在 | `H(B)` 可得 且 `DBh == H(B)` | DB 仍描述**旧**内容（K3） | 先删 T，再把 B 恢复为 T；**不得直接删 B** |
| **R4** T 存在、B 存在 | `DBh == null`（大文件策略）**或** `H(T)`/`H(B)` 任一侧不可得 | **无可信 hash，无法判定** | **保留 T 与 B 两份，不删不覆盖**；向用户报错并给出残留路径，由用户决定 |
| **R5** T 缺失、B 缺失、S 存在 | — | 上次崩在 K1 或 S4 中途 | 删 S（本次来源文件用户仍在手）；不改 DB |
| **R6** T 存在、B 缺失、S 存在 | — | 崩在 S4 中途 | 删 S；T 与 DB 均未动，安全 |
| **R7** B 存在但 `B.length() == 0` 或读取失败 | — | B **损坏** | **不得**用 B 覆盖 T；保留现场并报错（同 R4 的处理姿态） |

### 4.2 规则设计要点

1. **R1 优先于一切**：T 缺失时「恢复」是无歧义的 —— DB 指向的路径上没有文件，
   而 B 里有一份完整旧正文，恢复它只会让状态回到「DB 与内容一致」。
2. **R4 是本设计的核心立场**：**宁可留两份残留，也不猜**。
   特别是 `>32 MiB` 的 TXT（`DBh == null` 是既定策略值，不是「没有哈希」），
   以及「旧文件本来就大、新文件也大」的情形 —— **两侧都拿不到 MD5**，
   此时任何自动选择都可能把用户想要的那一份覆盖掉。
   故：**保留 + 报错 + 暴露路径**，把决定权交回用户。
3. **不得以删除或覆盖换取表面成功**：
   - 不允许「删掉 B 当作清理干净」（会销毁 K2 情形下仅存的正文）；
   - 不允许「无条件把 B 拷回 T」（会在 K4 情形下把已提交的新内容回退成旧内容，
     而 DB 仍写着新内容 ⇒ 制造 DB 与文件不一致，比崩溃本身更糟）；
   - 不允许「删 T 重来」（T 可能是唯一完好的新副本）。
4. **报错必须可操作**：错误信息要含 bookId、`T`/`B` 的绝对路径与两侧大小，
   便于用户/后续工具判断。**不得**只在日志里静默吞掉。

### 4.3 判定所需的最小辅助量

R2/R3 需要「`H(T)` 与 `H(B)` 各自可得」。为免在恢复时对大文件做全量 MD5（既慢又与本策略冲突），
判定前先做**尺寸短路**：

- `T.length != B.length` ⇒ 二者必不相同 ⇒ 结合 DB 的 `size` 与 `local_content_path`
  可缩小范围（若 `DB.size == T.length` 且 `DBp == T.path` ⇒ 倾向 R2；反之倾向 R3）。
  但**尺寸相同不蕴含内容相同**，所以尺寸只能用于**排除**，不能单独用于**确认**。
- 只有尺寸无法排除歧义时，才对 `≤32 MiB` 的一侧计算 MD5。

## 7. 仍不能解决的断电原子性

以下是本设计**明确不声称解决**的部分，必须在报告与后续验收里如实标注：

1. **单次 `rename()` 的元数据原子性可以依赖，但「多次 rename + 一次 DB 提交」的序列没有原子性。**
   本设计只能做到「崩溃后可判定、可恢复」，**做不到「崩溃后必然一致」**。
2. **写入 journal/标记本身也可能写一半。** 若标记文件内容残缺，判定退化为 §4 的 R4
   （保留 + 报错）。**不允许**把「标记读不出来」当成「没有标记」。
3. **`FileOutputStream` 的缓冲与 `fsync`**：当前代码没有显式 `fsync`。
   掉电时「已 `close()` 但未落盘」的数据仍可能丢失，而目录项也可能未持久化。
   本设计不引入 `fsync`（涉及性能与跨平台语义），因此**掉电场景下即使状态可判定，
   也可能判定在一份未真正落盘的文件上**。这是硬边界。
4. **DB 侧**：`runInTransaction` 保证 SQLite 事务原子性，但 **SQLite 的 WAL 与文件系统的
   持久化顺序**在掉电时同样不保证 —— 「DB 已提交、文件未落盘」或反之都可能出现。
   本设计把它们都归入 §4 的判定流程，但**不能保证判定结果与用户直觉一致**。
5. **`filesDir` 被系统清理 / 用户清数据**：不在本设计范围（属于备份产品，不是本修复）。
6. **并发**：若同一本书被两个入口同时修复（当前 UI 未提供，但未加锁），
   本设计的状态机不保证互斥 —— 需要额外的 per-book 互斥（**未设计**）。

## E1. R1 的反例（必须修掉的具体场景）

### E1.1 主反例：DB 已提交新内容，随后 T 才丢失

```
K4（S9 已提交、S10 未执行）   →  DB.content_hash = H(新正文), DB.size = 新长度, DBp = T
    ↓  之后 T 因外部原因消失
（外部原因，任一即可）
    · 用户在系统文件管理器/清理工具里动了应用私有目录
    · 部分数据恢复：从 zip 恢复时只覆盖了部分文件（LocalZipBackup.kt:111-121 是逐文件复制）
    · 存储配额回收 / 目录被系统清理
    · 上一轮修复改名后遗留：DBp 指向的旧名文件已不在，而本次 safeName 目录下留有旧 backup
    ↓
下次进入 reselectPlainText：T 不存在、B 存在
    ↓
旧 R1 ⇒「把 B 恢复为 T」
    ↓
✗ 结果：磁盘上是**旧正文**，DB 里却是**新 size / 新 content_hash / 新 path**
```

后果比「崩溃残留」本身更糟：

1. **阅读器读到的是旧内容**，而 UI/元数据（大小、来源基线）声称是新内容；
2. `books.content_hash` 与磁盘内容**不一致**，下游「内容是否更新」的比较（S04 系列）
   会以错误基线运行，可能反复报「可更新」或**永不报更新**；
3. 这是**静默**的 —— 没有任何一步会重新校验 hash，用户不会收到任何提示。

⇒ 结论：**T 缺失本身不构成恢复授权**。恢复的授权只能来自
「B 的内容确实就是 DB 所描述的那份内容」这一**正向证据**。

### E1.2 次反例：用户更换文件名

`ShelfImporter.kt:949-952`：

```kotlin
val safeName = fileName.replace(Regex("""[\\/:*?"<>|]"""), "_")  // 来自"本次所选文件"的显示名
val internalFile = File(internalDir, safeName)
val backup      = File(internalDir, "$safeName.backup")
```

`safeName` 派生自**本次所选文件**的显示名。若用户这次选的是改名后的副本，
则本次的 `T` 与 `B` 路径**都换了名字**，与 DB 的 `local_content_path` 不再对应。

由此产生一个 R1 会踩、但正文未覆盖的情形：

```
上一次成功修复：DBp = .../<旧名>.txt, DB.content_hash = H(旧名内容)
    ↓ 用户这次选了 <新名>.txt
本次：T = .../<新名>.txt  ← 不存在（首次用这个名字，**正常状态，不是崩溃**）
      B = .../<新名>.backup ← 存在（更早某次用同名的修复崩溃遗留）
    ↓
旧 R1 ⇒ T 不存在 + B 存在 ⇒ 「恢复」
    ↓
✗ 把一份**与 DB 无关**的旧残留写到了 DB 从未引用过的路径上
```

⇒ 新增边界（§E2 规则 **N8**）：当 `DBp` 的 basename ≠ 本次 `safeName` 时，
**本次的 T 不存在是预期状态**，不得当作崩溃证据；该目录下的任何残留 backup
**一律不得自动恢复**。

## E2. 修订后的判定表（取代正文 §4.1 的 R1–R7）

### E2.1 判据定义

| 符号 | 含义 | 可得性 |
|---|---|---|
| `T` | 本次目标路径 `internalDir/<safeName>` | — |
| `B` | `internalDir/<safeName>.backup` | — |
| `DBh` | `books.content_hash`（`CatalogEntities.kt:24`，可空） | — |
| `DBp` | `books.local_content_path`（可空） | — |
| `H(x)` | `x` 的 MD5 | **仅当** `x` 存在、`0 < x.length() ≤ 32 MiB` 时可计算；否则**不可得** |
| `matchesDB(x)` | `DBh != null && H(x) == DBh` | 仅当 `DBh != null` 且 `H(x)` 可得时才有真值；否则**不可判定** |
| `sameName` | `DBp` 非空 且 `basename(DBp) == safeName` | — |

**`>32 MiB` 的语义必须写清**：`DBh == null` 是**既定策略值**（`computeFileHash` 对大文件返回
`null`，见 `ShelfImporter.kt:438-452`），**不是**「这本书没有哈希」。
因此大文件下 `matchesDB` **永远不可判定** —— 不是 false，而是「问不出来」。

### E2.2 判定表

**前置**：任何规则都不得以「删除或覆盖」换取表面成功。命中 `保留` 的规则一律
**不改 DB、不删 T、不删 B**，并报出可操作的错误（含 bookId、`T`/`B` 绝对路径与两侧大小）。

| # | 情形 | 条件 | 判定 | 动作 |
|---|---|---|---|---|
| **N1** | T 缺失、B 存在 | `sameName` ∧ `matchesDB(B) == true` | **正向证据成立**：B 就是 DB 描述的那份内容，而 DB 指向的路径上没有文件 | **恢复 B → T**（逐字节校验后），保留 B 直至校验通过 |
| **N2** | T 缺失、B 存在 | `sameName` ∧ `DBh != null` ∧ `H(B)` 可得 ∧ `H(B) != DBh` | **B 不是 DB 描述的内容**（E1.1 主反例） | **保留现场 + 停止 + 报错**；**禁止**恢复 |
| **N3** | T 缺失、B 存在 | `sameName` ∧ `matchesDB(B)` **不可判定**（`DBh == null` 或 `H(B)` 不可得） | **无法判定** | **保留现场 + 停止 + 报错**；**禁止**恢复 |
| **N4** | T 存在、B 存在 | `matchesDB(T) == true` | DB 已提交 **T** 的内容；B 已过期（K4） | 保留 T；**删除 B** |
| **N5** | T 存在、B 存在 | `matchesDB(B) == true` ∧ `matchesDB(T) == false` | DB 描述的是 **B**；T 是未提交的新副本（K3） | 先删 T，再把 B 恢复为 T |
| **N6** | T 存在、B 存在 | 二者 `matchesDB` 均不可判定，或均不为 true | **无法判定** | **保留 T 与 B 两份 + 停止 + 报错** |
| **N7** | B 存在但不可用 | `B.length() == 0` ∨ 读取失败 ∨ `H(B)` 抛出 | **B 损坏** | **禁止**用 B 覆盖任何东西；保留现场 + 报错 |
| **N8** | `sameName == false`（用户换了文件名） | 与上列无关，**优先判定** | 本次 T 是 DB 未引用的新路径 | **禁止自动恢复任何残留 B**；若 B 存在 ⇒ 保留 + 报错；若 B 不存在 ⇒ **正常流程**（T 缺失是预期） |
| **N9** | T 缺失、B 缺失 | — | 无残留可恢复 | 清理 S（用户手上仍有来源文件）；不动 DB |
| **N10** | T 存在、B 缺失 | — | 正常 | 继续本次流程；S 可清理 |

**判定优先级**：`N7`（B 不可用）→ `N8`（换了名字）→ `N1`–`N6` → `N9`/`N10`。
`N7`/`N8` 命中时**不再**进入 N1–N6，避免用损坏备份或错配路径做恢复。

## E3. 修订后的设计要点（取代正文 §4.2）

1. **「T 缺失」不是证据，只是现象。** 只有 `matchesDB(B) == true` 才能授权恢复（N1）。
   正文 §4.2 要点 1 的「恢复是无歧义的」**予以撤回**。
2. **不可判定时一律保留现场。** `DBh == null`（大文件既定策略）或 `H` 不可得 ⇒
   判据「问不出来」，**不得**降级为「倾向某个分支」。
3. **长度与文件名只能用于排除，永远不能授权。** 正文 §4.3 的
   「`DB.size == T.length` ⇒ **倾向** R2」**予以撤回**：`T.length == B.length` 时二者仍可能
   内容不同，长度相同**不蕴含**内容相同。长度最多用来「排除某一侧」，不足以触发任何自动动作。
4. **不得以删除或覆盖换取表面成功**（保留正文该要点，并补一条）：
   - 补：**不得**为了「让本次修复继续下去」而把无法判定的残留 backup 删掉 ——
     那会在 E1.1 场景里销毁用户可能想留的那份正文。
5. **报错必须可操作**：含 bookId、`T`/`B` 绝对路径、两侧 size、`DBh` 是否为空、`sameName` 结论。
   **不得**只写日志静默吞掉。
6. **`matchesDB` 需要 hash，而 hash 可能不可得** ⇒ 本设计的自动恢复能力**天然受限于 32 MiB 策略**。
   若要让大文件也可自动恢复，必须先解决「大文件如何获得可信指纹」——
   见 §E5 的标记提案，**本轮不实施**。

## E5. 明确无法自动恢复的状态

以下状态**本轮设计明确不自动处理**，一律「保留现场 + 停止 + 报错」：

| 状态 | 触发规则 | 为何不能自动恢复 |
|---|---|---|
| DB 已提交新内容、T 事后丢失、B 为旧内容 | **N2** | 恢复会把旧正文配上新元数据（E1.1）—— 静默损坏 |
| 大文件（`DBh == null`）下的 T 缺失 / 双方存在 | **N3 / N6** | `DBh == null` 是策略值，`matchesDB` 问不出来 |
| `H(B)` 或 `H(T)` 计算失败（读取错误） | **N3 / N6** | 缺证据，不能猜 |
| 用户更换文件名后的任何残留 backup | **N8** | 该路径与 DB 无引用关系，恢复即错配 |
| B 损坏（0 字节 / 不可读） | **N7** | 用坏文件覆盖好文件 |
| T、B 都不匹配 `DBh` | **N6** | 两侧都不是 DB 描述的内容 |
| T 与 B 长度相同但内容不同 | **N6 / F10** | 长度不蕴含内容 |

**共同的硬限制**：`matchesDB` 依赖 MD5，而 MD5 只在 `≤32 MiB` 时可计算
（`ShelfImporter.kt:438-452` 的既定策略）。⇒ **所有 >32 MiB 的 TXT 都落在「无法自动恢复」**。

**可能的改进方向（本轮不实施，属提案）**：
在 S5 之前落一份**崩溃标记**（记录 intended new hash、old hash、old path），
使 N2/N3 在下次启动时可判定。但须注意正文 §7-2 已指出的限制：
**标记本身也可能写一半**，残缺标记只能退化为「保留 + 报错」，
**不得**把「标记读不出来」当成「没有标记」。该提案同时受 §7-3（无 `fsync`）与
§7-4（DB/WAL 持久化顺序）约束，**不能**彻底解决掉电原子性。

## E6. 仍未验证 / 未覆盖

1. **本节全部为静态推理，未运行任何测试**（本轮不跑 Gradle）。F1–F14 均为**待实现**的用例设计。
2. **`matchesDB` 的实际可用性未实测**：未验证真实数据中 `books.content_hash` 的填充率
   （导入路径是否总写 hash、旧记录是否为 null）。
3. **「T 事后丢失」的真实成因未取证**：E1.1 列出的几种外部原因
   （用户清理、部分恢复、配额回收）**均未在设备上复现或取证**，
   属**风险枚举**而非已证实事件。若实际不存在这类成因，N2 的触发概率会显著低于 E1.1 的叙述强度。
4. **N8 的判定依赖 `basename(DBp) == safeName`**，而 `safeName` 经过字符替换
   （`[\\/:*?"<>|]` → `_`）。DB 里存的是替换后的路径还是原始文件名，**本轮未核对**；
   若不一致，N8 会把「同名」误判为「换名」，从而**过度保守**（只会多报错，不会误恢复 —— 方向安全）。
5. **并发**：同一本书被两个入口同时修复时，本节状态机无互斥保证（同正文 §7-6）。
6. **掉电原子性**：本节不改善正文 §7 列出的全部边界。
