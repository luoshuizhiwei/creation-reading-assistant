## 0. 结论

1. **在全部当前约束下，不存在"可证明一致"的快照捕获方法。** 唯一具备可证明一致语义的通道是设备端在线 SQLite backup（`.backup` / `VACUUM INTO`，SQLite 自身文档保证的时点一致语义），但它被三重独立条件阻断：设备无 sqlite3；禁止推送二进制；且即使获准推送，targetSdk≥29 应用的 W^X/SELinux 执行策略使 app uid 执行外部二进制大概率不可行【平台模型·未实测】。→ **方案 A：BLOCKED，不设计绕行捷径。**
2. **唯一在当前操作约束下可执行的降级方法 = 零设备写的"同次流式打包三件套"**：`adb exec-out "run-as <pkg> tar -cf - databases"` → 主机重定向（db + wal + shm 同一次 tar 顺序读取）。执行层机制在本机有上一轮先例（`exec-out run-as tar` 全库导出 2,270,021,120 B、`tar -t` exit 0、解包副本 `PRAGMA integrity_check = ok`），**但先例先以 force-stop 制造冷态——"不 force-stop 的静默期变体"没有先例，其一致性只能达到"强证据链、不可形式证明"级**。这正符合前置审查 §6 预见的"退而求其次"路径：按其纪律，integrity_check 通过**只证明 SQLite 结构可读**，不证明捕获瞬间业务状态原子一致，也不证明恢复流程可用；恢复能力在任何演练或用户明确接受之前一律 **UNVERIFIED**。
3. **证据缺口（诚实登记）**：预检报告只含聚合值与哈希，**无逐条脱敏原始输出与退出码**；仓库检索证实三个聚合字节数（1,126,281,728 / 1,167,181,726 / 合计 2,293,468,585）在仓库中无任何第二记录。base.apk SHA-256 与字节数有 3 份既有记录交叉佐证；uid=10949 有 1 份既有记录佐证；"run-as 可用"与"设备无 sqlite3"**无法独立复核**。本窗口未操作手机补测；执行窗口 stage 0 必须现场重测（只读）。
4. 主机侧核验能力【已证实·本窗口实测】：Android SDK platform-tools 自带 sqlite3 CLI 3.50.6，Python 3.13.2 内置 sqlite3 模块 3.45.3——**副本的 integrity_check 与逐表清单可在主机侧完成，不依赖设备端任何工具**。
5. 最小用户决策清单见 §7；**安装两个沙箱 APK 是其中完全独立的一项，不并入任何其他决定，不构成默认授权。**

## 1. 评估对象与一致性语义基线

对象（源码锚点见前置审查 §5-D）：正式 Room 库 `creation_reading_assistant_native`（+wal/shm，`DatabaseModule.kt:56`、`AppDatabase.kt:159`）与 workdb `androidx.work.workdb`（+wal/shm），均在 `/data/data/<pkg>/databases/` 内。该应用进程是其数据库的唯一写者（WorkManager 的任务在该应用进程内执行）。

WAL 模式语义（SQLite 公开文档级，作为本评估的推理基线【平台模型·未实测于本设备】）：

- 提交先进 `-wal`，checkpoint 才并回主 db 文件；无写者活动时三者是静止的。
- **只拷主 db 不拷 wal**：丢掉全部"已提交未 checkpoint"事务——不是任何时点的一致快照。
- **捕获期间发生提交/checkpoint**（拷贝中途）：主文件与 wal 的帧盐/校验链可能错位，恢复时 wal 帧被截断或整体弃用——得到**撕裂快照**：可能丢失已提交事务或得到页级新旧混合状态。
- **`PRAGMA integrity_check` 通过**：只证明页结构/B-tree/索引自洽可读。**不**证明捕获瞬间业务状态原子一致，**不**证明恢复后业务状态正确，**不**证明恢复流程可用（P1 复核第 5 条、前置审查 §5-C-9）。任何情况下不得写成"已验证可恢复"。
- 文件级读取（cat/tar）不取任何 SQLite 锁：**对写者零阻塞，但也零保护**——一致性只能来自"捕获窗口内确实没有写者"。

## 2. 方案逐一评估

每方案列：所需设备写操作 / 对用户后台任务的影响 / 可验证的一致性证据 / 主机临时空间 / 无法满足的条件 / 判定。

### 方案 A：设备端在线备份（`run-as` + `sqlite3 .backup` / `VACUUM INTO`）

| 维度 | 评估 |
|---|---|
| 所需设备写 | ① 取得 sqlite3 二进制：设备没有，只能推送（推送即设备写，且被约束禁止）；② 执行本身在应用私有目录生成快照文件（若写进 `databases/` 还会扩大 §5-D-12 对账清单范围，若写 `cache/` 仍是生产应用私有目录写入） |
| 后台任务影响 | backup/VACUUM INTO 以读事务逐页拷贝：写者可能 SQLITE_BUSY 或被阻塞；若 WorkManager 任务恰在捕获窗口执行，run_attempt/状态变化会给 §5-D-13 对账引入需归因的差异 |
| 可验证证据 | **唯一具备可证明一致语义的方法**（SQLite backup 语义 = 捕获完成时刻的一致镜像）；证据：命令退出码、快照 integrity_check、从快照生成逐表清单 |
| 主机临时空间 | ≈ 快照体积（≤ 1.13 GB）+ 主机副本，≈ 1.2–2.3 GB |
| 无法满足的条件 | **设备无 sqlite3**【预检报告·无法独立复核】；**禁止推送二进制**（用户约束）；即使推送：untrusted_app/runas_app 域不可执行可写存储上的自定义二进制（Android 10+ W^X，targetSdk≥29）【平台模型·未实测】 |
| 判定 | **BLOCKED（三重不可满足）**。不设计绕行（如改 APK 内置、装辅助应用均属"修改正式应用/安装包"，同样被禁） |

### 方案 B：主机侧只读单文件拉取（只拉主 db，不含 wal）

| 维度 | 评估 |
|---|---|
| 所需设备写 | 无（`exec-out run-as cat databases/<主库>` 流式） |
| 后台任务影响 | 无锁、无干扰 |
| 可验证证据 | 有——但证据证明的是**不成立**：WAL 语义决定它必然丢失 wal 中已提交事务；databases 聚合 1.13 GB 中 wal 占比未知（预检未测，也不应在本窗口测），快照时效点不可知 |
| 主机临时空间 | ≈ 1.1 GB（浪费） |
| 无法满足的条件 | **构造性不足**：无论多安静，缺 wal 就不是任何时点的完整状态 |
| 判定 | **拒绝**（不是一致快照，作为恢复源或对账基准都不合格） |

### 方案 C：db+wal+shm 同次流式打包（`exec-out run-as tar` → 主机）——唯一可行降级

| 维度 | 评估 |
|---|---|
| 所需设备写 | **零**（tar 输出到 stdout，设备上不落任何临时文件；`databases/` 整目录一次打包，workdb 三件套自动包含） |
| 后台任务影响 | 文件级读取不取 SQLite 锁：对写者零阻塞、不取消/不改任何任务；代价仅 ≈1.1 GB 的 I/O 带宽（数十秒级）。风险与保护是同一枚硬币：若捕获窗口内恰有任务执行，产生撕裂快照——靠静默门 + 双通道证据发现，而不是靠机制阻止 |
| 可验证证据 | 四层证据链（见 §3 协议）：① 静默门 `pidof`（应用进程不存在 ⇒ 其库无任何可能写者，任务执行需先拉起该进程）；② 双通道两次 tar 字节级一致（窗口内稳态）；③ 主机副本 integrity_check（**仅结构**）；④ §5-D 内容级对账（真正的零变化证明）。合起来是**强证据链，但不是"捕获瞬间原子一致"的形式证明** |
| 主机临时空间 | DB 证据工作流：tar ≈1.13 GB/pass ×2 + 解包副本 ≈1.13 GB ≈ **3.4 GB 峰值**；完整档（加 files/ 1.17 GB + prefs）双通道 ≈ 4.6 GB + 解包 ≈ 2.3 GB ≈ **7 GB 峰值** |
| 无法满足的条件 | **无法满足"可证明一致"**（除非进程冻结或在线 backup）；shm 可由 db+wal 重建，同次打包仅为证据完整性 |
| 先例与缺口 | 机制先例【已证实·记录】：上一轮同机同应用 `exec-out run-as tar` 2,270,021,120 B、`tar -t` exit 0、解包副本 integrity_check ok——**但先例先 force-stop**；"不 force-stop + 静默门"变体【设备未知·无先例】 |
| 判定 | **当前约束下唯一可执行方法；一致性等级 = 强佐证·不可证明；恢复能力 UNVERIFIED 不因本方法改变** |

### 方案 D：force-stop 后冷拷贝

| 维度 | 评估 |
|---|---|
| 所需设备写 | force-stop 本身即状态修改（被用户约束明确禁止） |
| 后台任务影响 | 进程死亡：进行中的任务中断、JobScheduler 侧重排留痕——**改变了正被对账的环境本身**（§5-D-13 的任务字段可能因此出现需归因差异） |
| 可验证证据 | 近似冷态，文件级一致性最接近"可证明"（先例即此路径） |
| 主机临时空间 | 同方案 C |
| 无法满足的条件 | **用户约束直接禁止**；且会扰动被测状态 |
| 判定 | **BLOCKED（约束）**。若用户将来愿意放宽"不 force-stop"以换取更高一致性等级，属 §7 用户决策项，不是本评估可选择的捷径 |

### 方案 E：`adb backup`

Android 12+ 上该通道对应用数据已系统性弃用/收窄，Android 15 上不应作为应用数据通道【平台模型·未实测】；且触发即创建备份并在设备端弹确认。→ **拒绝**。

### 方案 F：运行设备上已安装的旧测试包（`com.creationreadingassistant.test`）借生产 uid 拷库

技术上不需要新安装，但这是**典型的绕安全门槛捷径，明确不设计**：① 在生产应用进程/uid 内执行未复审代码，其写入面不可预审（该包早于 qahost 隔离设计，34 类审计结论对它不适用）；② 它本身就扰动被对账的状态（workdb/prefs/日志）；③ 前置审查 §7-B6 禁止扩大测试范围；④ 既有记录另载 MIUI 阻断 Compose instrumentation（result code 102）。→ **拒绝**。

### 方案 G：应用内协作导出（给正式应用加备份代码路径/装辅助应用）

修改正式应用 + 重装 = 违反"不修改正式应用/不安装任何包"，且使 §5-D-10 的 base.apk SHA-256 对账项永久失配。→ **拒绝**。

### 方案 H：root / adb root

生产 MIUI 设备无 root 证据，授权范围外，且属常驻设备状态变更。→ **超范围，不设计**。

## 3. 方案 C 执行协议草案（**待用户批准；本窗口未执行任何一步**）

**stage 0 只读核验（执行窗口现场做，全部只读）：**
1. `adb devices` 唯一真实设备，逐条 `adb -s <serial>`（serial 脱敏记录）。
2. 重测并**留脱敏原始输出与退出码**：`run-as <pkg> id`；`which sqlite3`（预期仍无）；`pidof` 命令存在性；`tar --help` 退出码。
3. base.apk 三元组复测（路径/versionName/versionCode/SHA-256），与 §6 登记的既有记录值比对。

**捕获纪律（全部零设备写）：**
1. **静默门**：`adb shell pidof <pkg>` 捕获前与捕获后各一次，两次均为空（应用进程不存在 = 其库无可写者；WorkManager 任务执行前须拉起该进程）。
2. **双通道**：`adb exec-out "run-as <pkg> tar -cf - databases" > pass1.tar`，随后（进程仍不存在）重复得 pass2.tar；两文件 SHA-256 逐字节比对。**不等**≠立即失败：先用 `tar -tvf` 差异定位变更成员再归因，无法归因即 UNATTRIBUTED → 停。
3. **副本核验（只动副本）**：解包后先用副本**原始字节**算逐文件 SHA-256 留证；再用主机 sqlite3 CLI 3.50.6 或 Python sqlite3 3.45.3 打开副本跑 `PRAGMA integrity_check`——记录结果时**只允许写"结构完整性通过"**。
4. **内容级对账**：Room 逐表逐行规范化哈希、workdb 逐任务关键字段（`search_index_once_v1`/`search_index_daily_v1`/`reading_goal_reminder` 等，以现场 schema 为准）、书库逐文件路径+字节数+SHA-256、prefs 文件哈希——从副本生成，作为后续"测试后复测"的比对基准。副本打开恢复 wal 时会改写副本本身，故哈希取证必须在打开之前（或用第二份解包）。
5. **命名与隐私**：仓库只写方法、摘要、差异计数与中性称呼（"测试 EPUB"）；逐行/逐文件清单与原始 tar 只留仓库外本地私有目录，不入 git/docs/任何同步渠道。

**明确不可主张清单（写入执行报告的固定措辞）：**
- 不得写"业务状态原子一致"或"已验证一致的快照"，只能写"静默期双通道一致的副本"。
- integrity_check 只写"结构完整性通过"。
- 恢复能力一律写 **UNVERIFIED**，直到实机演练完成（演练是设备写操作，需单独授权）或用户书面接受"未经演练"。
