## 5. 进度账、交付格式与接续算法

### 5.1 每卡状态必须可追踪

统一状态：PLANNED → OWNED → OFFLINE_READY →（需要时DEVICE_READY/RUNNING）→ REVIEW_REQUIRED → ACCEPTED / ACCEPTED_WITH_LIMITS / PARTIAL / BLOCKED / REUSED。NOT_RUN单列验证维度，不当作整体失败。REUSED也要给原路径/指纹/适用理由。没有真实实施不得填OWNED/RUNNING。

每卡维护下列字段，可写入同一REPORT及state.continuationQueue的卡记录，不再造多套收据：

| 字段 | 要求 |
|---|---|
| cardId / 实际任务版本 / owner | 卡ID与全局任务分开；实际owner接任时填写 |
| baseline / changedFiles / beforeAfterSHA | 精确输入/实际变更；不拿mtime当指纹 |
| implementation / offline / emulator / recovery | 分别写状态和原证；编译绿不能覆盖设备红 |
| acceptedScope / limits / blocker | 用户结果、未验范围和具体阻塞，不写泛泛“待继续” |
| nextCard / unblockAction | 完成转哪卡；失败停哪些依赖；哪些独立工作继续 |
| report / readySHA / updatedAt | 原件路径、ready最后写、香港时间；processed非PASS |

### 5.2 每轮具体算法

1. 读取current/state指纹并核owner，找最前面的可执行卡；对已有同SHA充分结果直接复用。
2. 在该卡共用合同基础上补齐实际task版本、输入SHA、文件/缓存/锁、用户授权和owner，记录后才实施；没有必要选项不向用户追问。
3. 实施者闭环必要编译、定向验证和交付，接任Root核原证后裁决。可用独立核验则只覆盖本次高风险差量；不可用如实记同会话有限核验，不无限重试模型通道。
4. 成功同步current/state/matrix及nextCard，**直接进入下一项已授权可执行工作，不每卡末问“还继续吗”**。失败先安全收尾、保留原红、调整证据方法；仅暂停受阻依赖，不让独立工作跟停。
5. 同问题/同边界两轮无收敛或到预算点必须交具体证据、否定假说和改法；未知结果不得重发外部提示词/重跑旧scope。确需用户行动仅集中提出范围/权限/不可逆的一项具体问题。
6. 用户stop/Esc立即停新增输入，按已有安全恢复责任收口。额度将尽或换窗时写本卡精确进度和下一动作，不能把关键接续留在聊天里。
