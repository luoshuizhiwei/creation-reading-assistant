## 剩余 8 个架构级问题

### Q1 · MobileReaderView 巨型组件(1215 行)
- **位置**:`features/reader/MobileReaderView.tsx:59-1215`
- **现状**:单组件函数体 1150+ 行,30+ useState、10+ useRef、10+ useEffect、5+ 自定义 hook,所有状态/回调/effect 集中。子组件 ReaderPanel/ReaderSheets/EpubReaderView/TTSPlayerBar 均未 memo。
- **规模**:大(2-3 轮)。需拆出独立子组件(ReaderTopbar/ReaderBottomBar/ReaderErrorState/ReaderLoadingState) + 抽 hook(useReaderReminders 护眼/节奏、useReaderTTSControl)。
- **风险**:高。拆分易破坏布局/行为,需逐块验证。
- **建议方案**:
  1. 先抽最独立的:护眼提醒 + 节奏提示 effect → `useReaderReminders` hook(顺带修 P6 每秒触发)
  2. 抽渲染子组件:ReaderTopbar / ReaderBottomBar / ReaderErrorState(纯展示,props 传入)
  3. 子组件加 `React.memo`,减少重渲染范围(顺带修 P2)
- **优先级**:P2(可维护性 + 性能,但风险高,需充足测试时间)

### Q2 · ShelfPage 巨型组件(1310 行,3 组件挤一文件)
- **位置**:`features/shelf/ShelfPage.tsx:80-1113`(ShelfPage)、`1116-1238`(ImportHistoryPanel)、`1241-1310`(BatchTagManager)
- **现状**:主组件 1033 行,18 useState、8 useEffect,批量删除/撤销/标签/分类/书单/导入历史全堆一起。
- **规模**:大(2 轮)。拆 ShelfPage 的批量操作 → `useShelfBatchOps` hook;ImportHistoryPanel/BatchTagManager 拆到独立文件。
- **风险**:中高。批量操作逻辑复杂,拆分需保持撤销栈一致。
- **建议方案**:
  1. ImportHistoryPanel / BatchTagManager 拆到独立文件(低风险)
  2. 批量删除/撤销 → `useShelfBatchOps` hook
  3. 筛选/排序逻辑已有 shelf-selectors,确认无重复
- **优先级**:P2(可维护性)

### Q3 · openBook 函数过长(220 行)
- **位置**:`hooks/useMobileReaderBook.ts:259-480`
- **现状**:单函数 220+ 行,native reader 分支(L276-373)和 web engine 分支(L374-480)两条完全不同路径,多层 try/catch/async/闭包嵌套。
- **规模**:中(1 轮)。拆为 `openWithNativeReader` + `openWithWebEngine` 两个独立函数。
- **风险**:中。拆分需保持 abort/sequence 竞态控制一致。
- **建议方案**:
  1. 抽 `openWithNativeReader(book, ...)` —— native 路径(L276-373)
  2. 抽 `openWithWebEngine(book, ...)` —— web 路径(L374-480)
  3. openBook 只做分发 + 公共前置(clearContinueRemoval/pushHistory/setReaderBook)
- **优先级**:P3(可读性,不影响功能)

### Q4/F3 续 · saveMobileSnapshot 剩余增量化
- **位置**:`mobile-storage-books.ts`(5 处)、`mobile-storage-reading.ts:240`(1 处)
- **现状**:books 的 5 处涉及多表关联清理(删书清 books+progress+sessions+notes+highlights),不能简单传单 section。reading L240 待确认。
- **规模**:中(1 轮)。需改 mirrorSnapshotToSQLite 支持多 section 传入,或给 books 操作传 `["books","progress","sessions","notes","highlights"]` 多表数组。
- **风险**:低(只加参数,逻辑不变)。
- **建议方案**:
  1. 确认 `selectedSections` 支持数组多值(看 mirrorSnapshotToSQLite 实现)
  2. deleteMobileBook 传 `["books","progress","sessions","notes","highlights"]`(涉及的表)
  3. 其他 books 操作(更新书元数据)传 `["books"]`
  4. reading L240 按上下文传对应 section
- **优先级**:P1(性能,高频)

### P1 · 书架列表未虚拟化
- **位置**:`features/shelf/ShelfPage.tsx:787-805`(`filtered.map`)
- **现状**:直接 `.map` 渲染所有书。BookTile ~10 DOM 节点,500 本 = 5000 节点,滚动卡顿。同样问题:InspirationPage 灵感列表、BookDetailSheet 笔记列表。
- **规模**:中(1 轮)。引入 react-window 或自实现 windowing。
- **风险**:中。虚拟化需固定行高或动态测量,BookTile 高度可能不固定(书名换行)。
- **建议方案**:
  1. 优先用 `react-window` 的 `VariableSizeList`(支持动态高度)
  2. 或自实现:IntersectionObserver 只渲染可视区 + 缓冲行
  3. 网格视图(书架有列表/网格切换)需 `FixedSizeGrid`
  4. 同步改 InspirationPage
- **优先级**:P1(体验,大库必备)

### P2 · MobileReaderView 30+ useState 重渲染
- **位置**:`features/reader/MobileReaderView.tsx` 整体
- **现状**:currentProgress/currentChapter/currentPageInfo/readerControlsVisible/selectionText/readerNotice/ttsCharOffset 等高频变化,每次触发 1150 行组件树重渲染,子组件未 memo。
- **规模**:中(1 轮,与 Q1 拆分一并做)。
- **风险**:中。
- **建议方案**:
  1. Q1 拆分时给子组件加 `React.memo`
  2. 高频状态(currentProgress/currentPageInfo)改 ref + 节流强制更新,或拆到独立子组件局部 state
  3. readerControlsVisible 拆到 ReaderChrome 子组件,不影响正文区
- **优先级**:P1(与 Q1 一并,Q1 先行)

### P4 · 大 JSON.parse/stringify 阻塞主线程
- **位置**:`mobile-storage-core.ts:208`(parse)、`410`(stringify)
- **现状**:snapshot JSON 可能 5-10MB,同步 parse/stringify 阻塞主线程 100-500ms。已有 `mobile-reader-preparation.worker.ts` 先例,但 snapshot 序列化未走 worker。
- **规模**:大(1-2 轮)。需建 Web Worker,改 loadMobileSnapshot/saveMobileSnapshot 的 JSON 部分 offload。
- **风险**:中高。Worker 通信异步化,需改调用链(所有 saveMobileSnapshot 调用方)。
- **建议方案**:
  1. 新建 `mobile-snapshot-worker.ts`,暴露 parse/stringify
  2. saveMobileSnapshot:主线程 normalized 对象 postMessage 给 worker stringify,worker 返回字符串后 setItem
  3. loadMobileSnapshot:worker parse 字符串返回对象
  4. 或用 `structuredClone` + OffscreenCanvas 思路(但 JSON 操作 worker 最直接)
- **优先级**:P2(性能,但大库才明显;小库 100ms 可接受)

### P5 · epubjs(250KB)/jsqr(80KB)静态 import
- **位置**:
  - `reader/mobile-reader-epubjs.ts:1`(`import ePub from "epubjs"`)
  - `features/reader/components/EpubReaderView.tsx:2`
  - `features/reader/engine-v2/EpubReaderEngineV2.ts:1`
  - `components/QrScanOverlay.tsx:2`(`import jsQR from "jsqr"`)
- **现状**:epubjs 打入 MobileReaderView chunk,只读 TXT 也要下载。jsqr 打入主 bundle。
- **规模**:中(1 轮)。改动态 import,但 epubjs 调用处需改 async。
- **风险**:中。epubjs 在 3 处用,ePub(data) 创建 book 是同步调用,改 async 需调整渲染流程。
- **建议方案**:
  1. jsqr:QrScanOverlay effect 里预加载 `const jsQR = (await import("jsqr")).default`,scanFrame 用预加载变量(改动小)
  2. epubjs:在 EpubReaderView/mobile-reader-epubjs/EpubReaderEngineV2 里,把 `import ePub` 改为模块级 `let ePubModule: typeof import("epubjs") | undefined`,首次用时 `ePubModule ??= await import("epubjs")`,调用 `ePubModule.default(data)`
  3. 验证 Vite 自动 code-split(epubjs 独立 chunk,只在 epub 书时加载)
- **优先级**:P2(首屏体积,但只影响首启速度)

## 建议工作方式

1. **每个问题独立分支/提交**,便于回滚
2. **Q1/Q2 拆分前先写测试**(当前测试覆盖不全,拆分易引入回归)
3. **P1 虚拟化先做性能基准**(用 500 本书测滚动帧率,验证改前后)

5. 每个问题修完后 **重新打包 APK 让用户验证**,避免累积回归
